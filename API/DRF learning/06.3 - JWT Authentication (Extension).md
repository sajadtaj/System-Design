# اهداف این بخش

# مقدمه

در فصل 05 با Authentication آشنا شدیم.

# مشکل TokenAuthentication

در DRF کلاسیک:

کاربر Login می‌کند.

سیستم یک Token تولید می‌کند.

مثال:

```text
8c7e0a66f4d67f57f83e8d43d31c7d56
```

سپس تمام درخواست‌ها:

```http
Authorization: Token 8c7e0a66f4d67f57f83e8d43d31c7d56
```

را ارسال می‌کنند.

---

# محدودیت اول: وابستگی به Database

برای هر Request:

```text
Request
   ↓
Token
   ↓
Database Lookup
   ↓
User
```

سیستم مجبور است Token را از دیتابیس بخواند.

---

در پروژه‌ای با:

```text
100 Request / second
```

یعنی:

```text
100 Database Query / second
```

فقط برای Authentication.

    ↓

# ساختار JWT

هر JWT از سه بخش تشکیل می‌شود:

```text
HEADER
PAYLOAD
SIGNATURE
```

---

نمای کلی:

```text
HEADER.PAYLOAD.SIGNATURE
```

---

مثال واقعی:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

.

eyJ1c2VyX2lkIjoxLCJleHAiOjE3MzAwMDAwMDB9

.

m7d4Y2B4K4hG8Z5L3nD8...
```

# بخش اول: Header

Header مشخص می‌کند:

```text

الگوریتم امضا
```

مثال:

```json

    "typ": "JWT"
}
```

```text
Claims
```

است.

# Claims چیست؟

Claim یعنی:

```text

```

---

مثال:

```json
{
    "user_id": 1,
    "email": "user@example.com",

```

---

# بخش سوم: Signature

امنیت JWT توسط Signature تضمین می‌شود.

---

فرآیند:

```text
Header
+
Payload
+
SECRET_KEY
↓
Signature
```

---

اگر کسی Payload را تغییر دهد:

```text
Signature
نامعتبر می‌شود.
```

---

و Token رد خواهد شد.

# نکته بسیار مهم

JWT رمزنگاری (Encryption) نیست.

JWT امضاشده (Signed) است.

---

بنابراین:

```text
JWT را می‌توان Decode کرد.
```

---

اما:

```text
JWT را نمی‌توان
بدون Secret Key
جعل کرد.
```

# Access Token چیست؟

Access Token توکنی است که برای دسترسی به API استفاده می‌شود.

---

مثال:

```http
Authorization: Bearer ACCESS_TOKEN
```

---

معمولاً عمر کوتاهی دارد.

مثال:

```text
5 دقیقه

15 دقیقه

30 دقیقه
```

---

دلیل:

```text
اگر سرقت شد
بازه سوءاستفاده محدود باشد.
```

---

# Refresh Token چیست؟

Refresh Token برای دریافت Access Token جدید استفاده می‌شود.

---

معماری:

```text
Login
    ↓
Access Token
Refresh Token
```

---

کاربر:

```text
Access Token
```

را برای درخواست‌ها استفاده می‌کند.

---

وقتی Access Token منقضی شد:

```text
Refresh Token
```

به سرور ارسال می‌شود.

---

سرور:

```text
Access Token جدید
```

تولید می‌کند.

---

# چرا دو Token داریم؟

اگر فقط Access Token وجود داشته باشد:

```text
هر 5 دقیقه
کاربر باید Login کند.
```

---

اگر فقط Refresh Token وجود داشته باشد:

```text
امنیت کاهش پیدا می‌کند.
```

---

بنابراین:

```text
Access Token
=
عمر کوتاه

Refresh Token
=
عمر بلند
```

# Best Practices

1. فقط Access Token را به APIها ارسال کنید.
2. Refresh Token را در Endpointهای عادی استفاده نکنید.
3. تمام APIهای حساس را با IsAuthenticated محافظت کنید.
4. از HTTPS استفاده کنید.
5. Tokenها را در Log ذخیره نکنید.
6. Access Token را کوتاه‌عمر نگه دارید.

class LogoutAPIView(APIView):

    permission_classes = [
        IsAuthenticated
    ]

    def post(
        self,
        request
    ):

        refresh_token = request.data[
            "refresh"
        ]

        token = RefreshToken(
            refresh_token
        )

        token.blacklist()

        return Response(
            status=status.HTTP_205_RESET_CONTENT
        )
```

from rest_framework_simplejwt.serializers import (
    TokenObtainPairSerializer
)


class CustomTokenObtainPairSerializer(
    TokenObtainPairSerializer
):

    @classmethod
    def get_token(
        cls,
        user
    ):

        token = super().get_token(
            user
        )

        token["username"] = (
            user.username
        )

        token["email"] = (
            user.email
        )

        token["is_staff"] = (
            user.is_staff
        )

        return token
```

# نکته بسیار مهم

بسیاری از توسعه‌دهندگان تصور می‌کنند JWT به صورت پیش‌فرض
کاملاً Stateless است.

این تصور در DRF و SimpleJWT همیشه درست نیست.

در پیاده‌سازی پیش‌فرض:

JWTAuthentication

پس از اعتبارسنجی Token معمولاً User را از Database
بارگذاری می‌کند.

بنابراین:

Token
    ↓
Decode
    ↓
Database Lookup
    ↓
request.user

در بسیاری از پروژه‌ها همچنان رخ می‌دهد.

Stateless Authentication یک قابلیت جداگانه و اختیاری است
که باید آگاهانه فعال شود.

بنابراین:

JWT
≠
لزوم Stateless بودن

و نباید این دو مفهوم با یکدیگر اشتباه گرفته شوند.
