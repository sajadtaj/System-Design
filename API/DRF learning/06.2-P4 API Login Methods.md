# **06.2 - dj-rest-auth & django-allauth (Part 4)**

---

## اتصال dj-rest-auth به JWT

تا اینجا از Session Authentication استفاده کردیم.

اما در بسیاری از پروژه‌های امروزی مانند:

* Flutter
* React
* Vue
* Angular
* Mobile App

معمولاً از Session استفاده نمی‌شود.

در این پروژه‌ها معمولاً از:

```text
JSON Web Token (JWT)
```

استفاده می‌شود.

---

# چرا؟

Session وابسته به Cookie است.

اما برنامه‌های موبایل معمولاً Cookie ارسال نمی‌کنند.

در عوض:

```text
Login
      ↓
Access Token
      ↓
Authorization Header
      ↓
API
```

---

# نقش dj-rest-auth

خود dj-rest-auth وابسته به Session نیست.

بلکه می‌تواند:

* Session Authentication

یا

* JWT Authentication

را استفاده کند.

نوع رفتار آن با تنظیمات پروژه تعیین می‌شود.

---

# نصب Simple JWT

قبلاً در فصل 06.3 نصب کردیم.

در صورت نیاز:

```bash
pip install djangorestframework-simplejwt
```

---

# تنظیم Authentication

فایل:

```text
MyProject/config/settings.py
```

```python
REST_FRAMEWORK = {

    "DEFAULT_AUTHENTICATION_CLASSES": (

        "rest_framework_simplejwt.authentication.JWTAuthentication",

    ),

}
```

---

از این لحظه:

تمام Endpointهای محافظت‌شده

به جای Session

از JWT استفاده خواهند کرد.

---

# تنظیم dj-rest-auth

در نسخه‌های جدید dj-rest-auth تنظیمات از طریق دیکشنری `REST_AUTH` انجام می‌شود.

نمونه:

```python
REST_AUTH = {

    "USE_JWT": True,

}
```

این تنظیم باعث می‌شود Endpoint ورود (`/api/auth/login/`) به‌جای Session، توکن JWT تولید کند.

> **نکته:** نام و ساختار تنظیمات ممکن است بین نسخه‌های مختلف `dj-rest-auth` تغییر کند. همیشه تنظیمات را با نسخه‌ای که استفاده می‌کنید و مستندات رسمی همان نسخه تطبیق دهید.

---

# نتیجه Login

قبلاً پاسخ Login چیزی شبیه:

```json
{
    "detail": "Successfully logged in."
}
```

بود.

اکنون:

```json
{
    "access": "...",

    "refresh": "..."
}
```

برمی‌گردد.

---

# استفاده از Access Token

در تمام درخواست‌های بعدی:

```http
Authorization: Bearer <access_token>
```

ارسال می‌شود.

---

نمونه:

```http
GET /api/books/

Authorization: Bearer eyJhbGciOi...
```

---

# Refresh Token

Access Token معمولاً عمر کوتاهی دارد.

پس از پایان اعتبار:

Client باید:

```http
POST /api/token/refresh/
```

را فراخوانی کند.

---

نمونه:

```json
{
    "refresh": "..."
}
```

---

پاسخ:

```json
{
    "access": "..."
}
```

---

# Logout در JWT

در Session:

Logout یعنی حذف Session.

اما در JWT:

Token روی Client نگهداری می‌شود.

بنابراین Logout معمولاً یعنی:

* حذف Token از Client

یا

* Blacklist کردن Refresh Token

---

به همین دلیل در فصل **06.3 (JWT Authentication)** درباره Blacklist به‌صورت کامل صحبت خواهیم کرد.

# Session یا JWT؟

| ویژگی                          | Session         | JWT           |
| ----------------------------------- | --------------- | ------------- |
| نگهداری وضعیت           | روی سرور | روی Client |
| Cookie                              | دارد        | ندارد    |
| مناسب برای Django Template | بله          | خیر        |
| مناسب برای Flutter         | خیر          | بله        |
| مناسب برای React           | خیر          | بله        |
| مقیاس‌پذیری              | کمتر        | بیشتر    |

# اشتباه رایج

گاهی دیده می‌شود که در یک API، بدون نیاز واقعی، Session Authentication و JWT به‌صورت هم‌زمان برای همه کلاینت‌ها استفاده می‌شوند.

از نظر فنی این کار امکان‌پذیر است، اما باعث پیچیدگی در پیکربندی، تست و نگهداری می‌شود. بهتر است بر اساس نوع کلاینت و نیاز پروژه، روش احراز هویت را آگاهانه انتخاب کنید.

# جمع‌بندی

در این بخش یاد گرفتیم:
