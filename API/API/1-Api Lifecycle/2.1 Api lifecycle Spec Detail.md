
## ۱. این فایل اصلاً چیست؟

این یک **OpenAPI 3.1.0** Spec است؛ یعنی «قرارداد ماشین‌خوان» API تو.

* بک‌اند تو (Django + DRF) در عمل این رفتارها را پیاده کرده.
* این فایل، نسخهٔ رسمی/ماشینی همون رفتار است:
  * به انسان می‌گوید API چه شکلی است.
  * به ابزارها (Swagger UI, Postman, codegen) اجازه می‌دهد با API کار کنند.

در OpenAPI، معمولاً این بلوک‌های بالا-به‌پایین را داریم:

```yaml
openapi: 3.1.0
info: ...
servers: ...
paths: ...
components: ...
```

الان این چهار تا را داری؛ یعنی اسکلت اصلی کامل است.

---

## ۲. هدرهای سطح بالا (top-level keys)

### ۲.۱. `openapi: 3.1.0`

* این خط می‌گوید: این Spec مطابق نسخه **۳.۱.۰** استاندارد OpenAPI است.
* ابزارها براساس این عدد می‌فهمند چه قابلیت‌هایی اجازه دارند استفاده کنند.

---

### ۲.۲. `info: ...`

```yaml
info:
  title: Order Management API
  version: 2.0.0
  description: >
    Order Management API - Version 2
    ...
```

`info` متادیتای انسانی است:

* `title`: اسم رسمی API (برای UI‌ها و مستندات انسان‌خوان).
* `version`: نسخهٔ خود **Spec/API** (نه لزوماً کد). اینجا `2.0.0` یعنی API v2.
* `description`: توضیح طولانی انسانی:
  * اینجا توضیح می‌دهد نسخهٔ ۲ چه قابلیت‌های اضافه‌ای دارد:
    * `price_with_tax`
    * `items_count`, `total_amount`
    * embed شدن محصول در آیتم سفارش
    * سازگاری ورودی با v1

اگر بخواهی کامل‌ترش کنی می‌توانی توی info این‌ها را هم اضافه کنی (الان نداری):

* `termsOfService`
* `contact` (مثلاً ایمیل تیم)
* `license` (مثلاً MIT/Proprietary)

---

### ۲.۳. `servers: ...`

```yaml
servers:
  - url: http://127.0.0.1:8000/api/v2
    description: Local development server (v2)
  - url: https://api.example.com/v2
    description: Production (v2 placeholder)
```

هر `server` یعنی «کجا این API در دسترس است»:

* `url`: base URL برای تمام pathها.
  * پس `/products/` در عمل می‌شود:
    * `http://127.0.0.1:8000/api/v2/products/`
* `description`: توضیح انسانی؛ اینجا dev vs prod.

این بخش برای ابزارهایی مثل Swagger UI خیلی مهم است؛ می‌فهمند درخواست را به کجا بفرستند.

چیزهایی که می‌توانست اینجا باشد و نیست (optional):

* `variables` برای URLهای پارامتریک (مثلاً region, stage).

---

### ۲.۴. `paths: ...` – قلب رفتار HTTP

اینجا دقیقاً تعریف می‌کنی:

* چه URLهایی داریم (path).
* روی هر path چه methodهایی داریم (GET/POST/…).
* هر method چه پارامترهایی می‌گیرد و چه پاسخ‌هایی می‌دهد.

در Spec تو این pathها را داریم:

* `/products/`
* `/products/{product_id}/`
* `/users/{user_id}/orders/`
* `/orders/{order_id}/`

هر path خودش یک آبجکت است؛ داخلش عملیات (operation) قرار می‌گیرد: `get`, `post`, `patch`, …

مثلاً:

```yaml
/products/:
  get:
    tags: [Products]
    summary: List products (v2)
    ...
```

جزئیات operations را در بخش بعد باز می‌کنم.

---

### ۲.۵. `components: ...` – بلوک‌های قابل‌استفادهٔ مجدد

```yaml
components:
  schemas:
    ProductV2: ...
    OrderV2: ...
    ...
```

`components` جاهایی است که:

* مدل‌ها/اسکیماهای مشترک (schemas) را تعریف می‌کنی.
* در Spec کامل‌تر، می‌شد چیزهای زیر هم اضافه شود:
  * `parameters` (پارامترهای مشترک path/query/header)
  * `responses` (پاسخ‌های مشترک مثل 404, 422)
  * `securitySchemes` (تعریف JWT, OAuth2, API key)
  * `headers` و `examples` و `requestBodies` مشترک

الان تو فقط از `components.schemas` استفاده کرده‌ای، که برای شروع کاملاً اوکی است.

---

## ۳. zoom-in روی paths: ساختار یک endpoint

بیایم یکی از pathها را باز کنیم و الگو را ببینیم:

### ۳.۱. `/products/` + GET

```yaml
/products/:
  get:
    tags: [Products]
    summary: List products (v2)
    description: >
      Returns a list of products...
    operationId: listProductsV2
    responses:
      "200":
        description: List of products (v2)
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/ProductListV2"
```

در سطح operation (`get`) این فیلدها مهم‌اند:

1. `tags`
   * برای گروه‌بندی در UI مستندات (مثلاً تب "Products").
   * اینجا از tagهای متنی ساده استفاده کرده‌ای؛ می‌توانی در سطح root هم `tags:` را تعریف کنی و برای هر tag توضیح جداگانه بنویسی (الان نداری).
2. `summary`
   * توضیح یک‌خطی/کوتاه؛ معمولاً عنوانی که در UI نمایش داده می‌شود.
3. `description`
   * توضیح بلندتر، می‌تواند Markdown هم باشد.
   * اینجا رفتار v2 را توضیح می‌دهی (آن computed fieldها).
4. `operationId`
   * یک شناسهٔ یکتا برای این operation.
   * در codegen/SDK از این استفاده می‌شود (مثلاً client.products.listProductsV2()).
5. `parameters` (اینجا ندارد)
   * برای این مسیر نیازی نیست چون `/products/` path parameter ندارد و فعلاً query param هم تعریف نکرده‌ای.
6. `requestBody` (اینجا ندارد)
   * GET بدون body است، پس منطقی است که نداشته باشد.
7. `responses`
   * کلیدهایش status code هستند: `"200"`, `"404"`, `"422"`, …
   * زیر هر status:
     * `description`: توضیح انسانی.
     * `headers`: (اینجا نداری؛ می‌توانستی مثلاً `X-RateLimit-Remaining` تعریف کنی.)
     * `content`:
       * media type مثل `application/json`
       * و درون آن `schema` → شکل دادهٔ این پاسخ:
         * اینجا `$ref` به `ProductListV2`.

این pattern برای بقیه عملیات‌ها تکرار می‌شود، فقط بعضی‌ها `parameters` و `requestBody` هم دارند.

---

### ۳.۲. مثال کامل‌تر: `/products/{product_id}/` + GET

```yaml
/products/{product_id}/:
  get:
    tags: [Products]
    summary: Get product details (v2)
    ...
    parameters:
      - name: product_id
        in: path
        required: true
        description: Product identifier (e.g. "p-10")
        schema:
          type: string
    responses:
      "200": ...
      "404": ...
```

اینجا ساختار یک **پارامتر** را می‌بینی:

* لیست `parameters` → هر آیتم یک شیٔ `Parameter Object` طبق OpenAPI:
  * `name`: اسم پارامتر (`product_id`).
  * `in`: کجا قرار دارد؟
    * `path`, `query`, `header`, `cookie`.
  * `required`:
    * برای `in: path` طبق استاندارد **باید** true باشد.
  * `description`: توضیح انسانی.
  * `schema`: نوع داده:
    * اینجا `type: string`.

اگر query param هم داشتی، شبیه همین می‌بود، با `in: query`.

---

### ۳.۳. مثال با `requestBody`: `/users/{user_id}/orders/` + POST

```yaml
/users/{user_id}/orders/:
  post:
    tags: [Orders]
    summary: Create a new order for a user (v2)
    ...
    parameters:
      - name: user_id
        in: path
        required: true
        schema:
          type: integer
    requestBody:
      required: true
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/CreateOrderRequest"
          examples:
            valid:
              summary: Valid order creation
              value:
                items:
                  - product_id: "p-10"
                    qty: 1
                  - product_id: "p-11"
                    qty: 2
            invalid_empty_items:
              summary: Invalid - empty items
              value:
                items: []
    responses:
      "201": ...
      "404": ...
      "422": ...
```

`requestBody` خودش ساختار دارد:

* `description` (اینجا برای PATCH گذاشتی، برای POST هم می‌توانستی بگذاری).
* `required`: بدنه باید ارسال شود یا اختیاری است؟
* `content`:
  * کلید media type: `application/json`.
  * زیرش:
    * `schema`: شکل بدنهٔ ورودی.
    * `examples` یا `example`:
      * نمونه‌های واقعی از body که برای Document و تست مفیدند.

اینجا خیلی خوب عمل کردی: example معتبر و نامعتبر دادی؛ برای ابزارهای تست خودکار (مثلاً contract test) خیلی کمک می‌کند.

---

### ۳.۴. Responses با چند Status

هم برای `/users/{user_id}/orders/` و هم `/orders/{order_id}/` می‌بینیم که چند response داری:

* `"201"`: موفقیت در ایجاد.
* `"404"`: not found (user/product/order).
* `"422"`: validation error.

همه‌شان از `components.schemas` استفاده می‌کنند:

* `"201"` → `OrderV2`
* `"404"` → `NotFoundError`
* `"422"` → `ValidationError`

این کار باعث می‌شود:

* شکل خطاها استاندارد باشد.
* اگر بعداً چیزی در error model عوض شد، فقط در یک جای components تغییرش می‌دهی.

---

## ۴. zoom-in روی components.schemas

اینجا در واقع داری **مدل‌های API** را تعریف می‌کنی؛ عملاً تصویری از Serializerهای DRF تو.

### ۴.۱. `ProductV2`

```yaml
ProductV2:
  type: object
  description: Product representation for v2, including price_with_tax.
  properties:
    id: { type: string, example: "p-10" }
    title: { type: string, example: "Wireless Mouse" }
    price: { type: number, format: double, example: 450000.0 }
    price_with_tax: { type: number, format: double, ... }
  required:
    - id
    - title
    - price
    - price_with_tax
```

الگوی کلی Schema:

* `type`: نوع root (object/array/string/…).
* `description`: توضیح انسانی.
* `properties`: فیلدها و نوع هر کدام.
* `required`: فهرست فیلدهایی که **باید** در JSON باشند.
* `example`: نمونهٔ تک.
* در صورت نیاز:
  * `enum`, `minLength`, `maxLength`, `pattern`, …

در این Schema:

* `price_with_tax` یک فیلد **محاسبه‌شده** است؛ Spec این را فقط اطلاع‌رسانی می‌کند؛ خود محاسبه در بک‌اند است.

---

### ۴.۲. `ProductListV2`

```yaml
ProductListV2:
  type: array
  items:
    $ref: "#/components/schemas/ProductV2"
```

شکل کلی response `/products/`:

* یعنی یک آرایه از `ProductV2`.

---

### ۴.۳. `OrderItemV2`، `OrderV2`، `OrderListV2`

این‌ها مدل‌های خروجی v2 هستند:

* `OrderItemV2`:
  * `product_id`, `qty`, `price` → مثل v1.
  * `line_total` → computed.
  * `product` → nested `ProductV2`.
* `OrderV2`:
  * شناسهٔ سفارش، user_id، status، created_at…
  * `items` → آرایه‌ای از `OrderItemV2`.
  * `items_count`, `total_amount` → فیلدهای aggregate.
* `OrderListV2`:
  * آرایه‌ای از `OrderV2` (برای لیست سفارش‌ها).

اینجا mapping به دنیای Django تقریباً این است:

* Modelهای `Product`, `Order`, `OrderItem`.
* Serializerهای v2 که فیلدهای computed را اضافه می‌کنند.

---

### ۴.۴. Schemaهای ورودی (Create و Update)

* `CreateOrderItem` و `CreateOrderRequest`:
  * ساختار input برای POST `/users/{user_id}/orders/`.
  * `minItems: 1` روی items، و `minimum: 1` روی qty → قواعد validation.
* `UpdateOrderStatus`:
  * body برای PATCH `/orders/{order_id}/`.
  * `enum` برای status → ست رسمی وضعیت‌ها.

این‌ها معمولاً متناظر با Serializerهای **input** تو هستند.

---

### ۴.۵. Schemaهای خطا

* `ValidationError`:
  * فیلد `error`, `message`, `details`.
  * `details` با `additionalProperties: true` → Map از field→messageها.
* `NotFoundError`:
  * همان فرم استاندارد DRF:
    * `{ "detail": "Not found." }`

این تعریف‌های مشترک، حیات API را در v1/v2 و سرویس‌های دیگر خیلی تمیز می‌کند.

## ۵. چه چیزهایی معمولاً در Spec کامل‌تر هست و اینجا نیست؟

Spec تو برای v2 **کاملاً کاربردی** است، اما اگر بخواهیم آن را به سطح «production-grade همراه Governance» ببریم، چند چیز معمولاً اضافه می‌شود:

### ۵.۱. `security` و `components.securitySchemes`

الان هیچ‌جا نگفتی این API چطور secure می‌شود. در پروژه واقعی احتمالاً:

* JWT Bearer Token،
* یا Session auth،
* یا API Key در header است.

در Spec می‌توانستی این‌طور اضافه کنی (نمونه):

```yaml
components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

security:
  - BearerAuth: []
```

یا برای بعضی endpointها security را override کنی (مثلاً public vs private).

---

### ۵.۲. `tags` در سطح root

در بالای فایل، زیر info/servers، می‌توانی توضیحات غنی‌تر برای tagها بدهی:

```yaml
tags:
  - name: Products
    description: Operations related to product catalog.
  - name: Orders
    description: Operations for managing user orders.
```

الان فقط در سطح operation `tags: [Products]` استفاده کردی، که کافی هست، ولی این بخش root آن را غنی‌تر می‌کند.

---

### ۵.۳. `components.responses` و `components.parameters`

الان `NotFoundError` و `ValidationError` را به‌صورت **schema** تعریف کرده‌ای. می‌شود یک قدم جلوتر رفت:

* برای Errorهای متداول (۴۰۴، ۴۲۲، ۴۰۱، ۴۰۳) `responses` تکراری داری.
* می‌توانی یک `components.responses` بسازی، مثلاً:

```yaml
components:
  responses:
    NotFound:
      description: Resource not found
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/NotFoundError"
    ValidationFailed:
      description: Validation error
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ValidationError"
```

بعد در هر endpoint قشنگ می‌نویسی:

```yaml
responses:
  "404":
    $ref: "#/components/responses/NotFound"
  "422":
    $ref: "#/components/responses/ValidationFailed"
```

همین کار را برای پارامترهای تکراری مثل `user_id`, `order_id` هم می‌توانی در `components.parameters` انجام بدهی.

---

### ۵.۴. `headers` در responses

الان «هدرهای HTTP» را در سطح Spec تعریف نکرده‌ای؛ مثلاً:

* Rate limit headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`
* Correlation ID: `X-Request-ID`

OpenAPI اجازه می‌دهد برای هر response یا در `components.headers` آن‌ها را تعریف کنی. مثلاً:

```yaml
components:
  headers:
    X-Request-ID:
      description: Correlation ID for tracing
      schema:
        type: string
```

و در یک response:

```yaml
responses:
  "200":
    description: ...
    headers:
      X-Request-ID:
        $ref: "#/components/headers/X-Request-ID"
    content:
      application/json:
        schema: ...
```

اگر بخواهی ابعاد Observability را رسمی کنی، این خیلی مهم است.

---

### ۵.۵. موارد جانبی دیگر

که الان لازم نیست، ولی در Specهای mature دیده می‌شود:

* `externalDocs`: لینک به docs کامل یا wiki.
* `x-` extensions: فیلدهای vendor-specific برای ابزار داخلی (مثلاً `x-rate-limit-plan`).
* `servers` اختصاصی برای یک endpoint (مثلاً admin API در base URL جدا).

## ۶. جمع‌بندی ذهنی

اگر بخواهم تصویر ساده‌ای در ذهن تو بسازم:

* `info` → صفحهٔ اول کتاب API، عنوان و مقدمه.
* `servers` → آدرس‌هایی که این API در آن deploy شده.
* `paths` → فهرست فصل‌ها و زیر فصل‌ها:
  * هر path یک فصل.
  * زیرش GET/POST/… هر کدام یک «زیرمبحث» با:
    * پارامترها (ورودی path/query/header)
    * requestBody (بدنهٔ JSON)
    * responses (آنچه برمی‌گردد، با status code و schema)
* `components.schemas` → ضمیمهٔ کتاب که مدل داده‌ها را دقیق و مجزا توضیح می‌دهد.

چیزی که در پروژهٔ Django/DRF تو رخ می‌دهد این است:

* هر path+method تقریباً یک view/viewset method است.
* هر schema در components تقریباً یک serializer (یا چند serializer) است.
* رفتار واقعی کد باید با این Spec «هم‌خوان» باشد؛ هرجا diverge شود، API تو از Contract خارج شده.

اگر خواستی، در ادامه می‌توانیم:

* یکی از همین endpointها را بگیریم،
* و دقیقاً map کنیم به:
  * `Model`
  * `Serializer`
  * `View/ViewSet`
  * `urlpattern`
* و نشان بدهیم که این Spec چه‌طور مستقیماً روی ساختار جنگو/DRF می‌نشیند.
