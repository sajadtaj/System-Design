نقش شما:
شما یک معمار ارشد API و متخصص OpenAPI 3.1 هستید که تجربه‌ی عملی در طراحی APIهای نسخه‌دار با Django REST Framework دارید. موظفید یک مشخصات (Spec) کامل، دقیق و قابل استفاده در محیط واقعی برای API من تولید کنید.

استاندارد و رفرنس:

- از استاندارد OpenAPI نسخه 3.1.0 استفاده کن.
- منطق و ساختار را بر اساس مستندات رسمی OpenAPI و الگوهای رایج در پلتفرم‌های حرفه‌ای (Postman, Swagger, Kong, IBM API Connect, Red Hat 3scale) در نظر بگیر.
- هیچ endpoint یا فیلدی را از خودت اختراع نکن؛ فقط بر اساس اطلاعاتی که من می‌دهم طراحی کن. اگر جایی ابهام وجود دارد، با حداقل فرض معقول آن را حل کن و با یک کامنت `description` یا `x-note` در Spec توضیح بده.

ورودی‌ای که من می‌دهم (پایین‌تر خواهد آمد):

- توضیح دامنه‌ی کسب‌وکار: [توضیح دامنه، مثل Order Management, Trading, Portfolio ...]
- استک و فریم‌ورک: [مثلاً Django + DRF + PostgreSQL]
- استراتژی نسخه‌بندی: [مثلاً path-based: /api/v1, /api/v2]
- لیست منابع اصلی (Resources) و رفتارها:
  - [Resource 1: مسیرها، متدها، ورودی‌ها، خروجی‌ها، وضعیت‌ها]
  - [Resource 2: ...]
- مدل داده (Entityها و فیلدهای مهم + روابط): [Product, Order, OrderItem, User,...]
- روش احراز هویت/مجوز:
  - [مثلاً JWT Bearer، یا Session، یا API Key در header X-API-Key، یا بدون Auth]
- نیازهای غیرعملکردی مهم:
  - [مثلاً: pagination، فیلتر، مرتب‌سازی، Latency، error model یکسان، UTF-8، ...]
- الگوی خطا:
  - [مثلاً: { error, message, details } یا { detail }]

خروجی مورد انتظار:
یک فایل OpenAPI 3.1.0 به صورت YAML معتبر که بتوانم مستقیماً در ابزارهایی مثل Swagger UI / ReDoc / Postman / Kong استفاده کنم.

الزامات ساختار در خروجی:

1) سطح بالا (Top-level):

- فیلد `openapi` را روی `3.1.0` تنظیم کن.
- بلوک `info` را کامل پر کن:
  - `title`: [نام API، مثلا Order Management API]
  - `version`: [نسخه API، مثلا 1.0.0 یا 2.0.0]
  - `description`: توضیح چند خطی در مورد دامنه، نسخه فعلی، نکات مهم (مثلا فیلدهای محاسبه‌ای یا تفاوت با نسخه‌های قبل).
  - در صورت امکان `contact`, `license` و `termsOfService` را با مقدارهای معقول پیشنهادی و قابل ویرایش پر کن.
- بلوک `servers`:
  - حداقل دو server:
    - dev/local: [مثلاً http://127.0.0.1:8000/api/v1]
    - production placeholder: [مثلاً https://api.example.com/v1]
  - اگر نسخه‌ها در path هستند (مثل /api/v1), این را در urlها اعمال کن.

2) `tags`:

- برای هر گروه منطقی (مثلاً Products, Orders, Users, Auth) یک tag با `name` و `description` تعریف کن.
- این tags را در عملیات‌های زیر `paths` استفاده کن.

3) `paths`:

- برای هر endpoint که من در توضیحاتم می‌دهم، یک ورودی در `paths` بساز.
- برای هر path و method (GET, POST, PUT, PATCH, DELETE):
  - `tags`: گروه منطقی مرتبط (مثلاً Orders).
  - `summary`: یک خلاصه‌ی کوتاه و واضح.
  - `description`: توضیح بلندتر شامل نکات نسخه فعلی، فیلدهای محاسبه‌ای، رفتارهای خاص.
  - `operationId`: یکتا و معنادار (مثلاً listOrdersV1, createOrderV2, updateOrderStatusV1).
  - `parameters`:
    - برای path params (مثل {id}): `name`, `in: path`, `required: true`, `schema` با نوع مناسب (string/int).
    - برای query params (filter, pagination, search): `in: query`, `required` مناسب، `schema` با type و constraints (مثلاً min, max, enum).
  - در صورت نیاز `requestBody`:
    - `required`: true/false.
    - `content`:
      - برای `application/json`:
        - `schema`: تا حد امکان با `$ref` به `components.schemas` اشاره کن (مثلاً `CreateOrderRequest`).
        - حداقل یک `example` یا `examples` واقعی (valid/invalid) اضافه کن.
  - `responses`:
    - حداقل برای statusهای زیر (طبق توضیحات من و الگوهای رایج):
      - 2xx مناسب (200, 201, 204) با `description` واضح.
      - 400 (در صورت نیاز برای bad request).
      - 401/403 اگر Auth دارد.
      - 404 برای not found.
      - 422 برای خطای validation (اگر الگوی من این است).
      - 500 برای خطای داخلی سرور (generic).
    - در هر response:
      - اگر از الگوهای مشترک استفاده می‌کنی، ترجیحاً از `$ref` به `components.responses` استفاده کن.
      - برای responses با body JSON، `content.application/json.schema` را با `$ref` به schemaهای تعریف‌شده در `components.schemas` تنظیم کن.

4) `components`:

- `components.schemas`:
  - برای هر موجودیت دامنه (Product, Order, OrderItem, User, …) و هر ورودی/خروجی خاص (CreateOrderRequest, UpdateOrderStatus, ValidationError, NotFoundError, PaginatedList, ...) یک schema واضح تعریف کن.
  - از ویژگی‌های OpenAPI مثل `type`, `properties`, `required`, `enum`, `format`, `minItems`, `minimum`, `description`, `example` استفاده کن.
  - مدل خطا:
    - حداقل یک schema عمومی برای خطاها (مثلاً `ErrorResponse` یا `ValidationError`) با فیلدهای استاندارد و مثال مشخص بساز.
  - اگر API من pagination دارد:
    - یک schema عمومی برای لیست paginated (مثلاً `Paginated<T>`) طراحی کن یا حداقل برای هر لیست مهم یک schema شامل `results`, `count`, `next`, `previous` تعریف کن.
- `components.responses`:
  - responses مشترک مثل:
    - `NotFound`
    - `ValidationErrorResponse`
    - `Unauthorized`
    - `Forbidden`
    - `InternalServerError`
  - هر کدام با `description` و `content.application/json.schema` (با `$ref` به schemaهای خطا).
- `components.parameters`:
  - اگر پارامترهای تکراری مثل `user_id`, `order_id`, `page`, `page_size` وجود دارند، آن‌ها را این‌جا تعریف کن و در paths با `$ref` استفاده کن.
- `components.securitySchemes`:
  - بر اساس روش Auth که من مشخص می‌کنم:
    - اگر JWT Bearer: scheme http bearer با `bearerFormat: JWT`.
    - اگر API Key: type apiKey در header (مثلاً `X-API-Key`).
    - اگر Basic Auth: type http, scheme basic (فقط اگر صراحتاً گفته‌ام).
  - Root-level `security` را تنظیم کن تا نشان دهد کدام security به صورت پیش‌فرض روی تمام endpointها فعال است.
  - اگر بعضی endpointها public هستند، در همان operation `security: []` بنویس تا override شود.

5) الگوهای نسخه‌بندی:

- اگر API من چند نسخه دارد (مثلاً v1 و v2):
  - در `info.description` تفاوت نسخه فعلی را نسبت به نسخه‌های قبلی توضیح بده.
  - در `servers` یا `paths`، آدرس نسخه را اعمال کن (مثلاً /api/v1, /api/v2).
  - اگر لازم است، schemas را با پسوند نسخه نام‌گذاری کن (مثلاً `OrderV1`, `OrderV2`).

6) سبک YAML و خروجی:

- خروجی باید فقط شامل YAML معتبر OpenAPI باشد، بدون هیچ توضیح متنی خارج از Spec.
- indentها را دو فاصله‌ای بیاور (نه tab).
- جایی که منطقی است از `$ref` استفاده کن تا از تکرار جلوگیری شود.
- توضیحات (description) را تا حد امکان واضح و مختصر بنویس، ولی اگر لازم است نکته‌ای از فرضیات را آن‌جا مستند کن.

اگر جایی اطلاعات من کافی نبود:

- با حداقل فرض معقول، Spec را کامل کن.
- آن فرض را در `description` یا یک `x-note` توضیح بده تا بعداً بتوانم آن‌را ویرایش کنم.
