# فصل ۶ — پایش API (API Monitoring)

## ۱. API Monitoring دقیقاً چیست؟ نگاه یکپارچه به چند منبع

تقریباً همهٔ منابع جدی در این حوزه، از زاویه‌های مختلف یک چیز را می‌گویند.
Checkly وقتی از API Monitoring حرف می‌زند، روی این تأکید می‌کند که باید «عملکرد یک API را در طول زمان، با اندازه‌گیری دسترس‌پذیری، درستی داده و زمان پاسخ، زیر نظر بگیری» و این اندازه‌گیری‌ها را با آستانه‌های عملکرد مقایسه کنی. ([checklyhq.com][1])

ا Uptrends از زاویه دیگری به همان مفهوم می‌رسد و API Monitoring را «شکلی از پایش سنتتیک» می‌داند که سه چیز را دنبال می‌کند:
+ در دسترس بودن، 
+ درست بودن پاسخ‌ها و
+ عملکرد. 

ا یعنی API را مثل یک کاربر مصنوعی، بارها و بارها صدا می‌زند و نگاه می‌کند آیا واقعاً پاسخ درست و به‌موقع می‌دهد یا نه. ([uptrends.com][2])

SmartBear هم تعریف را به تولید نرم‌افزار نزدیک می‌کند: API Monitoring یعنی در محیط واقعی (Production)، APIها را زیر نظر بگیری تا «به دید کافی نسبت به عملکرد، دسترس‌پذیری و درستی تابع‌ها» برسی؛ و ابزار پایش، برایت مشخص می‌کند هر درخواست چقدر طول کشیده، چند بار فراخوانی شده، از کجا صدا زده شده و چقدر از زمان کل سیستم صرف آن شده است. ([SmartBear Software][3])

Middleware همین داستان را از منظر کسب‌وکار می‌گوید: کسب‌وکارها روی APIها سوار شده‌اند و آن‌قدر به آن‌ها وابسته‌اند که کوچک‌ترین افت در دسترس‌پذیری و عملکرد می‌تواند مستقیم روی تجربهٔ کاربر و درآمد اثر بگذارد؛ بنابراین API Monitoring ابزاری است برای «تضمین قابلیت اتکا (reliability)، دسترس‌پذیری و عملکرد». ([middleware.io][4])

اگر همهٔ این تعریف‌ها را جمع کنیم، می‌توانیم یک تعریف مهندسی و یک‌پارچه بسازیم:

> پایش API یعنی این‌که رفتار API را – از دید مصرف‌کننده‌اش – به‌طور مداوم و خودکار اندازه‌گیری و تحلیل کنیم:
> آیا در دسترس است؟ آیا درست جواب می‌دهد؟ آیا به‌اندازهٔ مورد انتظار سریع است؟ و آیا همچنان مطابق قراردادی است که در مستندات (Spec) برای آن نوشته‌ایم؟

این «دید از بیرون» نکتهٔ مشترک همهٔ منابع است: API Monitoring به منطق داخلی کد کاری ندارد؛ مهم این است که از بیرون، مثل یک کلاینت واقعی، چه تجربه‌ای از API می‌بینی.

## ۲. چرا API Monitoring در چرخهٔ عمر API حیاتی است؟

همهٔ این سایت‌ها، زود یا دیر، به دو سؤال جواب می‌دهند:
اگر API Monitoring نداشته باشی چه می‌شود؟ و اگر داشته باشی چه چیزی را واقعاً بهبود می‌دهد؟

Uptrends ساده می‌گوید: اگر API را مانیتور نکنی، خرابی‌ها و کندی‌های آن، مستقیم منجر به شکست سرویس‌ها، اپلیکیشن‌ها و سایت‌هایی می‌شود که روی آن بنا شده‌اند، و این یعنی تجربهٔ کاربری خراب و از دست رفتن اعتماد. ([uptrends.fr][5])

SmartBear روی وجه «visibility» تأکید دارد: بدون پایش، نمی‌فهمی API در محیط واقعی چه رفتاری دارد؛ ممکن است تست‌هایت همه سبز باشند، اما در لحظه‌ای که کاربران زیاد می‌شوند یا یک وابستگی بیرونی می‌لُنگد، API ناکارآمد می‌شود و تو تا وقتی شکایت کاربر نیاید، خبردار نمی‌شوی. ([SmartBear Software][3])

Checkly و Middleware این را با زبان SRE و DevOps ترجمه می‌کنند: پایش API ابزار تو برای مدیریت «قابلیت اتکا» است؛ چیزی که هم به شاخص‌های فنی مثل latency و error rate وصل است و هم به شاخص‌های کسب‌وکاری مثل نرخ تبدیل و درآمد. اگر KPI نداری، فقط «حس» می‌کنی سیستم خوب است یا بد؛ اگر monitoring و KPI داری، می‌توانی دقیق بگویی کجا و چرا خراب شده است. ([checklyhq.com][1])

در چرخهٔ عمر API که از طراحی و پیاده‌سازی و تست شروع می‌شود و به انتشار، نسخه‌بندی و بازنشستگی می‌رسد، Monitoring همان حلقه‌ای است که واقعیت Production را به تصمیم‌های بعدی برمی‌گرداند:
آیا باید نسخهٔ جدید را rollout کنیم یا فعلاً صبر کنیم؟ آیا v2 عملکرد قابل قبولی دارد یا باید مهم‌ترین مسیرها را دوباره طراحی کنیم؟ بدون دادهٔ مانیتورینگ، این تصمیم‌ها بیشتر شبیه حدس‌زدن هستند تا مهندسی.

## ۳. ابعاد اصلی پایش API: از سلامت تا قرارداد

منابع مختلف، دسته‌بندی‌های متفاوتی برای انواع پایش پیشنهاد می‌دهند؛
اما اگر آن‌ها را روی هم بیندازیم، چهار بُعد اصلی تقریباً در همه‌شان مشترک است: دسترس‌پذیری، عملکرد، کارکرد (functional correctness) و سازگاری با قرارداد (contract). ([checklyhq.com][1])

در بعد دسترس‌پذیری، سؤال ساده است:
«آیا API بالا است و به درخواست‌ها پاسخ می‌دهد؟»
در بعد عملکرد، می‌پرسی:
«با چه سرعتی پاسخ می‌دهد و در چه حجم ترافیکی شروع به لُنگ زدن می‌کند؟»
در بعد کارکرد، بحث این است که:
«آیا خروجی، از نظر منطق کسب‌وکار و سناریوهای واقعی، درست است؟»
و در بُعد قرارداد، نگاه می‌کنی که:
«آیا پاسخ‌ها هنوز با Spec رسمی (مثلاً OpenAPI) هم‌خوان هستند یا به‌مرور drift ایجاد شده؟»

Uptrends این مجموعه را به‌عنوان سه ستون availability، performance و functionality توصیف می‌کند و تأکید می‌کند که API Monitoring ذاتاً «synthetic» است؛ یعنی حتی اگر کاربر حقیقی‌ای در آن لحظه درخواست نفرستد، مانیتور تو باید همچنان API را صدا بزند و مراقب آن باشد. ([uptrends.com][2])

SmartBear هم روی همین سه‌گانه کار می‌کند و در ابزار AlertSite خودش، API Monitoring را دقیقاً حول این سه بُعد طراحی کرده: برای هر endpoint، هم درستی و سرعت call را می‌سنجد، هم از Spec یا تست‌های SoapUI/ReadyAPI به‌عنوان منبع قرارداد استفاده می‌کند تا فقط 200 OK بودن را کافی نداند. ([SmartBear Software][6])

این چهار بُعد، بستر مفهومی بقیه فصل را تشکیل می‌دهد: health check بیشتر به availability و readiness می‌پردازد، KPIها بیشتر برای performance و پایداری هستند، پایش سنتتیک پل بین functionality و contract است و نهایتاً SLA/SLI/SLO همین‌ها را به زبان تعهد و هدف تبدیل می‌کند.

## ۴. Health Check؛ کم‌هزینه‌ترین، اما حیاتی‌ترین لایه

همهٔ منابع روی یک نکته اتفاق نظر دارند: هر برنامهٔ پایش معقول، از یک Health Check ساده شروع می‌شود.
Checkly Health Check را یک call سبک می‌بیند که فقط باید نشان بدهد سرویس «زنده» است و اصلاً نباید با منطق سنگین یا وابستگی‌های پیچیده آغشته شود. ([checklyhq.com][1])

Uptrends هم همین را از زاویهٔ دیگری می‌گوید: Health Monitoring باید تا حد ممکن minimal باشد؛ اگر در Health Check همان کارهایی را بکنیم که در سناریوهای تجاری می‌کنیم، هم ریسک ایجاد خطاهای جعلی (false positive/negative) بالا می‌رود، هم خود Health Check به منبع فشار روی سیستم تبدیل می‌شود. ([uptrends.com][7])

در معماری مدرن، معمولاً دو نوع health endpoint تعریف می‌شود:

در نوع اول، liveness است؛ یعنی فقط می‌پرسد پروسهٔ سرویس هنوز زنده است یا نه. این endpoint نباید به پایگاه‌داده یا سرویس‌های بیرونی وابسته باشد. قرار است سریع جواب بدهد و برای systemd، Docker یا Kubernetes نقش «چک‌کردن نفس» سرویس را بازی کند.

در نوع دوم، readiness است؛ یعنی آیا سرویس واقعاً آمادهٔ پذیرش ترافیک است؟ این‌جا می‌توان به اتصال به پایگاه‌داده، دسترس‌پذیری صف پیام، وجود configuration لازم و موارد مشابه نگاه کرد. این endpoint می‌تواند کمی پیچیده‌تر باشد، اما باز هم نباید تمام منطق تجاری را اجرا کند.

هم Checkly و هم Uptrends روی این نکته تکیه می‌کنند که Health Check بخشی از monitoring است، اما خود monitoring نیست. اگر همهٔ monitoring را به یک health endpoint خلاصه کنی، فقط متوجه می‌شوی سرویس «کاملاً مرده» است؛ اما نمی‌فهمی در طول زمان چگونه پیر و فرسوده می‌شود، کند می‌شود، خطا می‌دهد یا رفتار business آن به‌تدریج خراب می‌شود. ([checklyhq.com][1])

## ۵. شاخص‌ها و KPIهای کلیدی در پایش API

وقتی منابع مختلف را کنار هم می‌گذاری، می‌بینی تقریباً همه‌شان به چند معیار کلیدی اشاره می‌کنند؛ فقط نام‌گذاری و زاویهٔ نگاه کمی فرق می‌کند. SmartBear از API Performance و Availability حرف می‌زند، Checkly از metrics که باید مانیتور شوند، Uptrends از performance و transaction data می‌گوید و Middleware فهرستی از KPIهای لازم برای مهندسی DevOps و observability ارائه می‌دهد. ([checklyhq.com][1])

اولین و بدیهی‌ترین شاخص، دسترس‌پذیری است. در ساده‌ترین حالت، uptime درصد زمانی است که API واقعاً پاسخ قابل‌قبول داده است. Uptrends این‌را در قالب synthetic monitoring پیاده می‌کند؛ از چند نقطهٔ جغرافیایی مختلف مرتب API را صدا می‌زند و طول زمان پاسخ و وضعیت آن را ذخیره می‌کند. اگر در بازه‌ای متوالی، پاسخ‌ها قطع شوند یا به خطا برسند، آن پنجره به‌عنوان downtime ثبت می‌شود. ([uptrends.com][2])

شاخص دوم، latency است؛ همان زمانی که طول می‌کشد API به یک درخواست جواب بدهد. SmartBear و Checkly هر دو روی این نکته تأکید دارند که میانگین ساده (average) معیار قابل اعتمادی نیست. برای دیده‌شدن رفتار واقعی سیستم، باید به percentiles نگاه کرد؛ معمولاً p50 برای تصویر کلی، و p90 و p95 و p99 برای دیدن انتهای توزیع که بیشترین رنج کاربر در آن خاطره می‌شود. اگر p95 در حالت عادی حدود ۲۰۰ میلی‌ثانیه است و یک‌باره به ۸۰۰ میلی‌ثانیه می‌رسد، حتی اگر میانگین خیلی تغییر نکرده باشد، از دید تجربهٔ کاربر سیستم خراب شده است. ([checklyhq.com][1])

سومین شاخص مهم، نرخ خطاست؛ یعنی نسبت درخواست‌هایی که به خطای 5xx یا 4xx غیرمنتظره ختم شده‌اند به کل درخواست‌ها. منابعی مثل Middleware و SmartBear، روی این تأکید می‌کنند که نگاه خام به تعداد خطا کافی نیست؛ باید نسبت آن خطاها را در ارتباط با سطح ترافیک ببینی، و همچنین تفکیک کنی که آیا خطا در endpoint حیاتی رخ داده یا در مسیرهای حاشیه‌ای. ([middleware.io][4])

شاخص‌های دیگری هم مطرح می‌شوند: حجم ترافیک (throughput)، تعداد time-outها، اندازهٔ payload، تغییرات ناگهانی در اندازهٔ پاسخ‌ها (که ممکن است نشانهٔ regression یا نشت داده باشد) و نسبت موفقیت در سناریوهای چندمرحله‌ای. اما چیزی که در همهٔ منابع مشترک است این است که این اعداد فقط زمانی معنا پیدا می‌کنند که برایشان baseline و آستانه تعریف کرده باشی. تا وقتی نمی‌دانی شکل «عادی» پاسخ‌گویی API چیست، هیچ ابزاری نمی‌تواند به‌صورت هوشمند بگوید وضعیت «غیرعادی» شده است. ([middleware.io][4])

## ۶. پایش سنتتیک و سناریوهای چندمرحله‌ای

Checkly عملاً API Monitoring را معادل Synthetic Monitoring گرفته است؛ یعنی به‌جای این‌که صرفاً روی لاگ‌های واقعی تکیه کنی، خودت به‌عنوان یک «کاربر مصنوعی» مرتب API را صدا بزنی و سناریوهای مختلف را از ابتدا تا انتها طی کنی. Uptrends هم API Monitoring را در مجموعهٔ ابزار Synthetic Transaction Monitoring قرار می‌دهد و نشان می‌دهد که چطور می‌توانی یک «مسیر خرید» یا «جریان تجاری» را به چند مرحلهٔ پشت‌سرهم تبدیل کنی و از طریق مانیتورینگ آن مسیر، مشکلات را زودتر ببینی. ([checklyhq.com][1])

ایده این است که خیلی وقت‌ها، مشکل API در یک endpointِ جدا دیده نمی‌شود، بلکه در اتصال چند endpoint به هم خودش را نشان می‌دهد. مثلاً در سناریوی یک سیستم سفارش، ممکن است:

درخواست دریافت لیست محصولات به‌خوبی کار کند؛
درخواست ایجاد سفارش (POST) نیز ظاهراً OK باشد؛
اما وقتی سفارش را دوباره GET می‌کنی، وضعیت آن به‌غلط ثبت شده باشد؛
یا PATCH برای تغییر وضعیت سفارش رفتار ناپایداری داشته باشد.

پایش سنتتیک این سناریو را به چند گام تبدیل می‌کند:
در گام اول، محصولات را می‌خوانی؛ در گام دوم، یک سفارش جدید می‌سازی؛ در گام سوم، همان سفارش را می‌خوانی و مقایسه می‌کنی؛ در گام چهارم وضعیت آن را تغییر می‌دهی و دوباره چک می‌کنی که آیا تغییر اعمال شده است یا نه. در هر گام، assertionهایی داری که فقط به status code نگاه نمی‌کنند، بلکه فیلدهای کلیدی پاسخ را بررسی می‌کنند. Checkly حتی روی این تأکید می‌کند که باید بتوانی روی بدنهٔ JSON با JSONPath یا عبارات منظم assertion تعریف کنی تا صرفاً 200 OK بودن را موفقیت تلقی نکنی. ([checklyhq.com][1])

Uptrends این‌گونه جریان‌ها را multi-step API transactions می‌نامد و در مستنداتش نشان می‌دهد که چطور یک جریان خرید یا ورود کاربر را می‌شود بدون نیاز به رابط کاربری (UI) و فقط در سطح API، سناریو کرد و روی آن مانیتور گذاشت. این نوع پایش، فاصله‌ی بین «تست واحد» و «تجربهٔ پیوستهٔ کاربر» را پر می‌کند؛ چیزی که برای سیستم‌های نسخه‌محور و متکی بر API (مثل آن‌چه تو می‌سازی) حیاتی است. ([uptrends.com][7])

## ۷. هشدار و مدیریت رخداد؛ کِی و چگونه باید خبر بدهی؟

Monitoring بدون Alerting، مثل دوربین مداربسته‌ای است که هیچ‌وقت کسی فیلمش را نگاه نمی‌کند.
SmartBear در بحث API Monitoring روی این نکته تأکید می‌کند که هدف، صرفاً جمع‌کردن داده نیست؛ باید مشخص شود چه زمانی وضعیت از «نرمال» به «مسئله‌دار» تغییر کرده و چه پیامی با چه سطح اهمیتی، به کدام کانال ارسال شود. ([SmartBear Software][3])

Checkly هم هشدار می‌دهد که استفادهٔ خام از alertها، به سرعت به «خستگی هشدار» (alert fatigue) منجر می‌شود؛ یعنی تیم آن‌قدر نوتیفیکیشن بی‌اهمیت دریافت می‌کند که در لحظهٔ بحران واقعی هم دیگر حوصلهٔ توجه کردن ندارد. راه‌حل آن‌ها این است که alert را بر اساس KPIها و SLOها تنظیم کنی، نه بر اساس حس و حدس. ([checklyhq.com][1])

به تعبیر ترکیبی منابع، یک جریان هشدار خوب این ویژگی‌ها را دارد:
قبل از کاربر نهایی متوجه مشکل می‌شود؛
فقط زمانی فعال می‌شود که یک SLI مشخص از محدودهٔ SLO عبور کرده باشد؛
اطلاعات کافی برای شروع تحقیق را در خود پیام حمل می‌کند (مثلاً endpoint، region، زمان، نمونهٔ پاسخ)؛
در کانال‌هایی می‌رود که افراد درست آن‌جا حضور دارند (مثلاً Slack، ایمیل، PagerDuty یا ابزارهای Incident Management دیگر). ([middleware.io][4])

وقتی Monitoring را در کنار Alerting قرار می‌دهی، تازه یک چرخهٔ کامل Incident Response شکل می‌گیرد: مانیتور، مشکل را کشف می‌کند؛ alert، تیم مناسب را مطلع می‌کند؛ تیم، از طریق داده‌های telemetry و logs و traces دنبال علت می‌گردد؛ مشکل fix می‌شود و در نهایت، SLI دوباره به محدودهٔ هدف (SLO) برمی‌گردد. بدون این حلقهٔ آخر، Monitoring فقط یک داشبورد زیباست که در لحظات بحران، به کار واقعی نمی‌آید.

## ۸. SLA، SLI و SLO؛ ترجمهٔ پایش به زبان تعهد و هدف

جایی که SmartBear و Middleware هر دو روی آن تأکید می‌کنند، همین پیوند بین Monitoring و SLA/SLO است. آنچه تو در ابزار مانیتورینگ اندازه‌گیری می‌کنی، SLI است: شاخص‌های واقعی مانند درصد دسترس‌پذیری، latency p95، نرخ خطای 5xx. SLO هدفی است که برای این SLI تعیین کرده‌ای؛ مثلاً می‌گویی API عمومی تو باید حداقل ۹۹٫۹ درصد از زمان، در طول یک ماه، در دسترس باشد؛ یا latency p95 نباید از ۳۰۰ میلی‌ثانیه بالاتر برود. SLA هم تعهد قراردادی تو به مشتری است که معمولاً روی همین SLOها سوار می‌شود و اگر نتوانی به آن‌ها برسی، جریمه یا امتیازی برای مشتری در نظر گرفته می‌شود. ([SmartBear Software][3])

Monitoring بدون اتصال به SLO، تبدیل به سیلی از نمودارها می‌شود که کسی نمی‌داند کدام‌شان مهم‌تر است. وقتی SLI و SLO را تعریف کرده باشی، آن نمودار‌ها و عددها ناگهان معنا پیدا می‌کنند: اگر در نیمهٔ ماه، error rate به‌صورتی پایدار روی ۳ درصد ایستاده، و SLO تو حداکثر ۱ درصد بوده، یعنی error budgetی که در ابتدای ماه داشتی، تقریباً تمام شده است و باید جلوی rollout تغییرات جدید را بگیری تا وضعیت را تثبیت کنی. این نگاه از دنیای SRE گوگل وارد این بحث شده و حالا در اغلب مقالات راهنمای Monitoring و Observability از جمله منابعی که نگاه کردیم، به‌طور مستقیم یا غیرمستقیم دیده می‌شود. ([middleware.io][4])

در عمل، این یعنی Monitoring فقط یک گزارش پسینی نیست؛ تبدیل می‌شود به ابزاری که سرعت توسعه، میزان ریسک و زمان انتشار نسخه‌های جدید را کنترل می‌کند. آن‌چه در نمودارهای زمان‌-پاسخ و نرخ خطا می‌بینی، مستقیم روی تصمیم‌های roadmap اثر می‌گذارد.

## ۹. نقش ابزارها؛ از Postman و Checkly تا Middleware و Uptrends

هر چهار منبعی که بررسی کردیم، علاوه بر توضیح مفاهیم، ابزار هم معرفی می‌کنند. Checkly، خودش را به‌عنوان «پلتفرم پایش API و monitoring-as-code» معرفی می‌کند که اجازه می‌دهد checkهای HTTP و جریان‌های چندمرحله‌ای را به‌صورت کد تعریف کنی، روی زمان‌بندی‌های مختلف اجرا کنی و روی نتیجهٔ آن alert بسازی. ([checklyhq.com][8])

Uptrends، مجموعه‌ای از مانیتورهای synthetic برای وب‌سایت، API و تراکنش‌های چندمرحله‌ای ارائه می‌کند و تمرکز خاصی روی پایش چندمکانی (multi-location) و بدون نیاز به کدنویسی دارد؛ یعنی می‌توانی از طریق رابط کاربری، یک سناریوی API را ضبط و تنظیم کنی و بعد از چند نقطهٔ جغرافیایی مختلف آن‌را اجرا کنی. ([uptrends.com][9])

SmartBear، خانواده‌ای از ابزارها را کنار هم چیده است: ReadyAPI و SoapUI برای تست عملکرد و کارکرد، و AlertSite برای پایش در محیط واقعی. نکتهٔ جالب در ساختار آن‌ها این است که موارد تستی (test cases) که در مرحلهٔ توسعه استفاده می‌کنی را می‌توانی تقریباً بدون تغییر، به مانیتورهای AlertSite تبدیل کنی؛ یعنی مرز بین «تست قبل از انتشار» و «پایش بعد از انتشار» تا حد زیادی محو می‌شود. ([SmartBear Software][6])

Middleware از سمت دیگری وارد می‌شود و خود را به‌عنوان پلتفرم observability معرفی می‌کند که پایش API بخشی از آن است. در این مدل، داده‌های مربوط به API (latency، error rate، throughput، مسیرها، متادیتا) در کنار دیگر telemetryها (مانند log و trace) ذخیره و تحلیل می‌شوند، و همین کمک می‌کند تا «ریشهٔ مشکل» سریع‌تر پیدا شود، نه فقط نشانه‌های سطحی آن. ([middleware.io][4])

نکتهٔ مشترک این ابزارها، نه در جزئیات امکانات‌شان، بلکه در فلسفهٔ کارشان است:
اول، API را از بیرون و به‌صورت synthetics می‌بینند؛
دوم، داده‌های حاصل را به KPI و SLI ترجمه می‌کنند؛
سوم، بر اساس آن، هشدار و تصمیم‌گیری را خودکار یا نیمه‌خودکار می‌کنند.

## ۱۰. جمع‌بندی: Monitoring به‌عنوان ستون Reliability در API Lifecycle

اگر بخواهیم همهٔ این روایت‌ها را در یک جمله جمع کنیم، می‌توان گفت API Monitoring در نگاه این منابع، فقط یک «ماژول جانبی» نیست؛ بلکه هستهٔ رویکردی است که می‌خواهد مطمئن شود APIها – به‌عنوان ستون فقرات نرم‌افزار مدرن – نه‌فقط کار می‌کنند، بلکه «همیشه و به‌درستی و با کیفیت مناسب» کار می‌کنند. ([checklyhq.com][1])

Health Check به تو می‌گوید API مرده است یا نفس می‌کشد.
KPIها نشان می‌دهند این نفس، تند و بی‌رمق است یا آرام و منظم.
Synthetic Monitoring نشان می‌دهد در جریان‌های واقعی کسب‌وکار چه اتفاقی می‌افتد.
Alerting تضمین می‌کند که در لحظهٔ بحران، کسی واقعاً متوجه می‌شود.
و SLA/SLI/SLO این همه را به زبان هدف‌ها و تعهدها ترجمه می‌کنند.
