# تعریف و ریشه‌شناسی RESTful API

RESTful API، که مخفف Representational State Transfer Application Programming Interface است، یک سبک معماری نرم‌افزاری برای طراحی APIهای وب است که بر سادگی، مقیاس‌پذیری و استقلال لایه‌ها تأکید دارد. واژه REST از رساله دکتری روی فیلدینگ در سال ۲۰۰۰ گرفته شده و به معنای "انتقال حالت نمایشی" است، جایی که "حالت نمایشی" به داده‌های قابل دسترس (مانند JSON) اشاره دارد که کلاینت‌ها برای تغییر وضعیت منابع استفاده می‌کنند. این سبک نه یک پروتکل سفت‌وسخت، بلکه مجموعه‌ای از اصول هدایت‌کننده است که APIها را به گونه‌ای طراحی می‌کند تا مانند صفحات وب پویا عمل کنند. درک این ریشه‌شناسی به شما کمک می‌کند تا ببینید چرا RESTful API پایه اکثر سیستم‌های مدرن مانند میکروسرویس‌ها شده است – تصور کنید API را مانند یک کتابخانه دیجیتال ببینید که هر کتاب (منبع) آدرس دقیق (URI) دارد و شما با دستورات ساده (متدهای HTTP) آن را قرض می‌گیرید یا برمی‌گردانید.

## تاریخچه و تکامل RESTful API

REST در سال ۲۰۰۰ توسط روی فیلدینگ در رساله دکتری خود در دانشگاه کالیفرنیا معرفی شد، به عنوان پاسخی به پیچیدگی‌های پروتکل‌های قدیمی مانند SOAP که بر پایه XML و قراردادهای سنگین بودند. در دهه ۲۰۱۰، با ظهور اپلیکیشن‌های موبایل و ابری، RESTful API به استاندارد غالب تبدیل شد و HTTP/2 در ۲۰۱۵ سرعت و کارایی آن را افزایش داد. تا سال ۲۰۲۵، تکامل آن شامل ادغام با HTTP/3 (برای کاهش تأخیر) و تمرکز بر API-first design شده است، جایی که APIها پیش از UI طراحی می‌شوند.

### جدول زمانی تکامل کلیدی

| سال       | رویداد کلیدی                          | تأثیر بر RESTful API                     |
|-----------|---------------------------------------|------------------------------------------|
| ۲۰۰۰     | رساله فیلدینگ                        | معرفی اصول پایه مانند statelessness     |
| ۲۰۰۸     | ظهور JSON به عنوان فرمت اصلی          | جایگزینی XML برای سادگی و سرعت          |
| ۲۰۱۵     | HTTP/2 و multiplexing                 | بهبود عملکرد در ترافیک بالا             |
| ۲۰۲۰     | OpenAPI 3.1                           | استانداردسازی مستندسازی               |
| ۲۰۲۵     | HTTP/3 و AI-driven API management     | بهینه‌سازی برای IoT و هوش مصنوعی        |

این تکامل نشان می‌دهد که RESTful API از یک ایده آکادمیک به ابزاری صنعتی تبدیل شده؛ با تمرکز بر این تاریخچه، می‌توانید تصمیمات طراحی آگاهانه‌تری بگیرید و به بعد اصول کلیدی گذار کنید.

## اصول کلیدی RESTful API

اصول RESTful API بر شش قید محدودکننده (constraints) بنا شده که هر کدام برای حفظ سادگی و مقیاس‌پذیری طراحی شده‌اند. این اصول مانند قوانین یک بازی هستند که بدون آن‌ها، سیستم‌ها پراکنده و غیرقابل نگهداری می‌شوند. برای مثال، در اپلیکیشن اسنپ، اصل client-server اجازه می‌دهد UI موبایل مستقل از سرور تکامل یابد.

### جدول شش اصل اصلی

| اصل                  | توضیح مختصر                                      | مثال کاربردی                          |
|----------------------|--------------------------------------------------|---------------------------------------|
| Client-Server       | جداسازی کلاینت (UI) از سرور (داده)              | اپ موبایل دیجی‌کالا بدون تغییر سرور |
| Stateless           | هر درخواست مستقل و کامل اطلاعات را دارد         | لاگین با JWT بدون ذخیره session      |
| Cacheable           | پاسخ‌ها قابل کش یا غیرقابل کش مشخص می‌شوند     | کش لیست محصولات در مرورگر            |
| Uniform Interface   | رابط یکنواخت با URI، نمایندگی‌ها و HATEOAS     | متدهای HTTP استاندارد برای همه منابع |
| Layered System      | لایه‌های میانی مانند CDN بدون آگاهی کلاینت     | پروکسی برای بارگذاری در نتفلیکس     |
| Code on Demand      | ارسال کد اجرایی از سرور (اختیاری و نادر)        | جاوااسکریپت برای گسترش کلاینت        |

### اصل statelessness و تأثیر آن بر طراحی

ا Stateless بودن یعنی سرور هیچ اطلاعاتی از درخواست‌های قبلی ذخیره نمی‌کند؛ هر درخواست باید تمام زمینه (context) لازم را حمل کند. این ویژگی مقیاس‌پذیری را افزایش می‌دهد زیرا سرورها می‌توانند بدون هماهنگی state کار کنند، اما چالش‌هایی مانند مدیریت session با توکن‌ها (مانند JWT) ایجاد می‌کند. در مقایسه با sessionهای stateful قدیمی، statelessness امنیت را بهبود می‌بخشد زیرا هیچ داده حساسی روی سرور نمی‌ماند. برای مثال، در API تلگرام Bot، هر پیام ارسال‌شده stateless است و توکن API کل زمینه را فراهم می‌کند – این را عمیقاً درک کنید تا در طراحی میکروسرویس‌ها موفق شوید.

### uniform interface و HATEOAS

ا Uniform Interface رابطی یکنواخت فراهم می‌کند که شامل شناسایی منابع با URI، دستکاری از طریق نمایندگی‌ها (representations)، پیام‌های خودتوصیف (self-descriptive)، و HATEOAS (Hypermedia as the Engine of Application State) است. HATEOAS پیشرفته‌ترین بخش است: API لینک‌های hypermedia (مانند "next_page" در JSON) ارائه می‌دهد تا کلاینت بدون دانش قبلی ناوبری کند. در سال ۲۰۲۵، با روند API productization، HATEOAS برای کشف‌پذیری در ابزارهای AI حیاتی شده است. مثلاً در API اسپاتیفای، لینک‌های "related_artists" کلاینت را هدایت می‌کند – این اصل را تمرین کنید تا APIهای پویاتری بسازید.

## ساختار و اجزای اصلی RESTful API

ساختار RESTful API بر پایه منابع (resources) استوار است: هر موجودیت (مانند کاربر یا پست) یک منبع است که با URI شناسایی می‌شود. نمایندگی (representation) آن منبع – معمولاً JSON – داده را توصیف می‌کند، و متدهای HTTP عملیات را تعریف می‌کنند. این ساختار مانند یک نقشه شهری است که هر خیابان (URI) به مقصد (منبع) منتهی می‌شود.

### منابع، URI و نمایندگی‌ها

URIها باید سلسله‌مراتبی و معنادار باشند، مانند /v1/users/123/orders. نمایندگی‌ها فرمت‌هایی مانند JSON (رایج‌ترین در ۲۰۲۵) یا XML هستند که metadata و لینک‌ها را شامل می‌شوند. مثال JSON برای یک سفارش در دیجی‌کالا:

```json
{
  "id": 456,
  "user_id": 123,
  "items": [
    {"product_id": 789, "quantity": 2}
  ],
  "total": 150000,
  "links": {
    "self": "/v1/orders/456",
    "payment": "/v1/orders/456/payment"
  }
}
```

### متدهای HTTP و کدهای وضعیت

متدها عملیات را مشخص می‌کنند: GET برای خواندن، POST برای ایجاد، PUT برای جایگزینی کامل، PATCH برای به‌روزرسانی جزئی، و DELETE برای حذف. کدهای وضعیت (Status Codes) موفقیت یا خطا را نشان می‌دهند، مانند ۲۰۱ Created برای POST موفق.

| متد     | هدف                  | کد موفقیت معمول | Idempotent؟ |
|---------|----------------------|-------------------|-------------|
| GET     | خواندن               | ۲۰۰ OK            | بله         |
| POST    | ایجاد                | ۲۰۱ Created       | خیر         |
| PUT     | جایگزینی کامل        | ۲۰۰ OK            | بله         |
| PATCH   | به‌روزرسانی جزئی     | ۲۰۰ OK            | خیر         |
| DELETE  | حذف                  | ۲۰۴ No Content    | بله         |

این اجزا را در پروژه‌هایتان اعمال کنید تا APIهای استاندارد بسازید.

## ویژگی‌های پیشرفته و بهترین روش‌ها

ویژگی‌های پیشرفته مانند pagination (صفحه‌بندی) و filtering (فیلترسازی) برای مدیریت داده‌های بزرگ ضروری هستند. در ۲۰۲۵، با روند async APIs، پشتیبانی از درخواست‌های غیرهمزمان (مانند streaming JSON) رو به افزایش است.

### نسخه‌بندی و pagination

نسخه‌بندی (versioning) تغییرات را مدیریت می‌کند: URI versioning (/v2/users) رایج‌ترین است، اما header versioning (Accept: application/vnd.myapi.v2+json) انعطاف‌پذیرتر. Pagination با query params مانند ?page=2&limit=10 انجام می‌شود. مثال: در API OpenAI (ChatGPT)، versioning برای مدل‌های جدید استفاده می‌شود – این روش‌ها را برای جلوگیری از شکست کلاینت‌های قدیمی به کار ببرید.

### مدیریت خطاها

خطاها باید با فرمت Problem Details (RFC 7807) برگردانده شوند: JSON با type، title، status و detail. مثلاً برای ۴۰۴ Not Found:

```json
{
  "type": "https://example.com/errors/not-found",
  "title": "منبع یافت نشد",
  "status": 404,
  "detail": "کاربر با ID 123 وجود ندارد"
}
```

این رویکرد شفافیت را افزایش می‌دهد و debugging را آسان می‌کند.

## امنیت و عملکرد در RESTful API

امنیت و عملکرد دو وجه مکمل هستند: statelessness امنیت را با کاهش ذخیره‌سازی state بهبود می‌بخشد، اما نیاز به احراز هویت قوی ایجاد می‌کند.

### احراز هویت و محدودیت نرخ

از JWT یا OAuth2 برای authentication استفاده کنید؛ API Keys برای سادگی. Rate Limiting (مانند ۱۰۰ درخواست در دقیقه) از سوءاستفاده جلوگیری می‌کند. CORS برای کنترل دسترسی کلاینت‌ها ضروری است، و HTTPS اجباری. در APIهای IoT مانند Tuya، OAuth2 برای دستگاه‌های امن استفاده می‌شود – امنیت را اولویت دهید تا سیستم‌هایتان مقاوم بمانند.

### بهینه‌سازی کش و فشرده‌سازی

Cache-Control و ETag هدرها پاسخ‌ها را قابل کش می‌کنند. Gzip برای فشرده‌سازی JSON حجم را کاهش می‌دهد. در ۲۰۲۵، با HTTP/3، QUIC پروتکل تأخیر را کم می‌کند. مثال: نتفلیکس از CDN برای کش محتوای API استفاده می‌کند – این تکنیک‌ها سرعت پروژه‌هایتان را دوچندان می‌کنند.

## مقایسه با فناوری‌های جایگزین

RESTful API ساده است، اما در سناریوهای پیچیده محدودیت دارد. مقایسه با GraphQL (انعطاف‌پذیر اما پیچیده‌تر) یا gRPC (باینری و سریع برای میکروسرویس‌ها) کمک می‌کند انتخاب درستی کنید.

### جدول مقایسه کلیدی

| ویژگی              | RESTful API              | GraphQL                  | gRPC                     | SOAP                     |
|---------------------|--------------------------|--------------------------|--------------------------|--------------------------|
| فرمت داده          | JSON/XML                 | JSON                     | Protocol Buffers         | XML                      |
| پروتکل             | HTTP/1.1+                | HTTP                     | HTTP/2                   | HTTP/SOAP                |
| stateless          | بله                      | بله                      | بله                      | خیر (stateful ممکن)     |
| مناسب برای          | وب/موبایل عمومی         | کوئری‌های پیچیده        | میکروسرویس‌های داخلی   | سیستم‌های سازمانی      |
| پیچیدگی            | پایین                    | متوسط                    | بالا                     | بسیار بالا              |
| روند ۲۰۲۵         | API-first + AI           | Federation               | Streaming                | Legacy                   |

REST برای ۸۰% موارد ایده‌آل است، اما برای real-time از WebSocket استفاده کنید – این مقایسه را برای انتخاب آگاهانه به یاد آورید.

## کاربردها و مثال‌های واقعی

ا RESTful API در صنایع متنوع کاربرد دارد: در وب (دیجی‌کالا برای جستجوی محصولات با GET /v1/search)، موبایل (اسنپ برای POST /trips درخواست سفر)، سرگرمی (اسپاتیفای برای GET /playlists پلی‌لیست‌ها)، هوش مصنوعی (OpenAI برای POST /chat/completions پرامپت‌ها)، IoT (Xiaomi برای PATCH /devices/status به‌روزرسانی سنسورها)، و بازی (PUBG backend برای GET /matches لیست مسابقات). این مثال‌ها نشان می‌دهند RESTful چقدر انعطاف‌پذیر است – آن‌ها را در پروژه‌هایتان شبیه‌سازی کنید.

## ابزارها و فریم‌ورک‌ها برای پیاده‌سازی

ابزارها پیاده‌سازی را تسریع می‌کنند: FastAPI (پایتون) برای سرعت و مستندسازی خودکار، NestJS (جاوااسکریپت) برای TypeScript.

### مثال کد با FastAPI (پایتون)

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from typing import List

app = FastAPI(title="نمونه RESTful API", version="1.0.0")

class User(BaseModel):
    id: int
    name: str
    email: str

users: List[User] = []

@app.get("/v1/users", response_model=List[User])
def get_users(skip: int = 0, limit: int = 10):
    return users[skip: skip + limit]

@app.post("/v1/users", response_model=User, status_code=201)
def create_user(user: User):
    users.append(user)
    return user

@app.get("/v1/users/{user_id}", response_model=User)
def get_user(user_id: int):
    for user in users:
        if user.id == user_id:
            return user
    raise HTTPException(status_code=404, detail="کاربر یافت نشد")
```

این کد یک API ساده stateless با pagination می‌سازد – آن را اجرا کنید تا اصول را لمس کنید.

## مستندسازی و تست RESTful API

مستندسازی با OpenAPI/Swagger ضروری است: ابزارهایی مانند Redoc UI برای خوانایی. تست با Postman یا Insomnia برای end-to-end، و pytest برای unit tests. در ۲۰۲۵، ابزارهای AI-driven مانند Apidog تست خودکار را اضافه کرده‌اند – مستندسازی را بخشی از کدتان کنید تا همکاری آسان شود.

## روندهای نوظهور در ۲۰۲۵

در ۲۰۲۵، روندهایی مانند API productization (API به عنوان محصول)، security mesh (امنیت توزیع‌شده)، و ادغام AI (مانند auto-generation docs با LLMها) RESTful را تحول می‌دهند. async APIs برای streaming داده‌ها (مانند در IoT) و low-code tools مانند DreamFactory سرعت را افزایش می‌دهند. این روندها REST را برای آینده آماده می‌کنند – با آن‌ها آشنا شوید تا پیشرو بمانید.
