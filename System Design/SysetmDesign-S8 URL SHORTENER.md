# مقدمه شخصی قبل از کتاب

## URL Shortener یعنی چه؟

فرض کنید یک آدرس خیلی بلند داریم مثل:

> `https://www.example.com/products/shoes/men/sneakers?color=red&size=42&discount=summer2024`

حالا این آرد را در یک سرویس کوتاه‌کننده مثل `short.link/abc123` خلاصه می‌کنیم. هرکس این لینک کوتاه را بزند، به همان لینک بلند اصلی هدایت می‌شود.

## ۳ اصل ساده برای درک معماری آن (برای تازه‌کارها)

### ۱. ذخیره نگاشت (Mapping)
یک دیتابیس ساده داریم که در آن جفت‌های `(کلید کوتاه, لینک اصلی)` را نگه می‌دارد:

| Short Code | Original URL |
|------------|--------------|
| abc123     | https://example.com/خیلی/بلند |
| def456     | https://google.com/... |

### ۲. فرآیند کوتاه‌کردن (Write)
- کاربر لینک بلند می‌دهد → سیستم یک کد منحصربه‌فرد (مثلاً تصادفی ۶ حرفی) می‌سازد → ذخیره در دیتابیس → برگرداندن `base_url/کد`

### ۳. فرآیند هدایت (Read / Redirect)
- کاربر `short.link/abc123` را می‌زند → سرور کد `abc123` را از دیتابیس پیدا می‌کند → یک **HTTP 301 یا 302 Redirect** به لینک اصلی می‌فرستد.

> ۳۰۱ = دائمی (مرورگر کش می‌کند)  
> ۳۰۲ = موقتی (هر بار می‌پرسد)

## چرا در طراحی معماری مهم است؟

### نکته‌هایی که باید بدانی:
- **مقیاس‌پذیری**: ممکن است میلیون‌ها لینک کوتاه داشته باشی → باید دیتابیس خیلی سریع با کلید `code` جستجو کند (ایندکس).
- **طول کد کوتاه**: اگر ۶ حرف (حروف + عدد) = حدود ۵۶ میلیارد ترکیب (۶۲^6).
- **کلید یکتا**: چطور از تکراری نشدن کدها مطمئن شوی؟ روش‌هایی مثل:
    - استفاده از **Base62 Encoding** از یک ID عددی افزایشی در دیتابیس
    - یا تولید تصادفی با چک کردن تکراری نبودن
- **ردیرکت سریع**: بهترین کار استفاده از **Web Server** مثل Nginx یا CDN برای این کار است بدون اینکه بار زیادی روی اپلیکیشن سرور بیاید.
- **آنالیز**: خیلی‌ها تعداد کلیک‌ها، موقعیت جغرافیایی و ... را هم ذخیره می‌کنند (یعنی دیتابیس آنالیتیکس جدا).

## یک تمرین ساده برای شروع (خیلی ابتدایی)

اگر بخواهی با یک `map` در حافظه بسازی (فقط برای تمرین):

```python
shortener = {}  # کلید: کد کوتاه, مقدار: آدرس بلند

def shorten(long_url):
    code = "abc123"  # باید الگوریتم بدی برای تولید یکتا
    shortener[code] = long_url
    return f"short.link/{code}"

def redirect(code):
    return shortener.get(code, "not found")
```

## اشتباه رایج تازه‌کارها

- **ذخیره کل URL بدون validation**: ممکن است یکی `javascript:alert(1)` بزند یا لینک خیلی بلندی که دیتابیس را اذیت کند.
- **استفاده از Redirect نوع 302 برای لینک‌هایی که همیشه ثابت هستند** (بهتر است 301 برای سئو و سرعت).
- **طراحی کلید کوتاه با طول متغیر** که جستجو را سخت می‌کند.

# ترجمه کتاب اصلی 

## طراحی سرویس کوتاه‌کننده URL (مانند TinyURL)

در این فصل، به یک سؤال جالب و کلاسیک مصاحبه طراحی سیستم می‌پردازیم: طراحی سرویس کوتاه‌کننده URL مانند tinyurl.

### مرحله ۱ - درک مسئله و تعیین محدوده طراحی

سؤالات مصاحبه طراحی سیستم عمداً باز (open-ended) طراحی می‌شوند. برای طراحی یک سیستم خوب، پرسیدن سؤالات شفاف‌کننده حیاتی است.

**کاندیدا:** آیا می‌توانید مثالی بزنید از اینکه یک کوتاه‌کننده URL چگونه کار می‌کند؟
**مصاحبه‌کننده:** فرض کنید URL اصلی به این صورت است:
`https://www.systeminterview.com/q=chatsystem&c=loggedin&v=v3&l=long`
سرویس شما یک نام مستعار (alias) با طول کوتاه‌تر ایجاد می‌کند:
`https://tinyurl.com/y7keocwj`
اگر روی نام مستعار کلیک کنید، شما را به URL اصلی هدایت (redirect) می‌کند.

**کاندیدا:** حجم ترافیک چقدر است؟
**مصاحبه‌کننده:** روزانه ۱۰۰ میلیون URL تولید می‌شود.

**کاندیدا:** طول URL کوتاه‌شده چقدر است؟
**مصاحبه‌کننده:** تا حد امکان کوتاه.

**کاندیدا:** چه کاراکترهایی در URL کوتاه‌شده مجاز هستند؟
**مصاحبه‌کننده:** URL کوتاه‌شده می‌تواند ترکیبی از اعداد (۰-۹) و حروف (a-z، A-Z) باشد.

**کاندیدا:** آیا می‌توان URLهای کوتاه‌شده را حذف یا به‌روزرسانی کرد؟
**مصاحبه‌کننده:** برای سادگی، فرض می‌کنیم URLهای کوتاه‌شده قابل حذف یا به‌روزرسانی نیستند.

در اینجا موارد استفاده پایه (basic use cases) آورده شده است:

1. **کوتاه‌سازی URL:** دریافت یک URL بلند => بازگرداندن یک URL بسیار کوتاه‌تر
2. **هدایت URL:** دریافت یک URL کوتاه‌تر => هدایت به URL اصلی
3. **ملاحظات در دسترس بودن بالا، مقیاس‌پذیری و تحمل‌پذیری خطا (fault tolerance)**

#### تخمین پشت پاکت (Back of the envelope estimation)

- **عملیات نوشتن:** روزانه ۱۰۰ میلیون URL تولید می‌شود.
- **عملیات نوشتن در ثانیه:** ۱۰۰ میلیون / ۲۴ / ۳۶۰۰ = ۱۱۶۰
- **عملیات خواندن:** با فرض نسبت عملیات خواندن به نوشتن ۱۰:۱، عملیات خواندن در ثانیه: ۱۱۶۰ * ۱۰ = ۱۱,۶۰۰
- با فرض اینکه سرویس کوتاه‌کننده URL به مدت ۱۰ سال اجرا شود، باید از ۱۰۰ میلیون * ۳۶۵ * ۱۰ = ۳۶۵ میلیارد رکورد پشتیبانی کنیم.
- فرض کنید میانگین طول URL ۱۰۰ بایت است.
- **نیاز ذخیره‌سازی طی ۱۰ سال:** ۳۶۵ میلیارد * ۱۰۰ بایت = ۳۶.۵ ترابایت (TB)

مهم است که مفروضات و محاسبات را با مصاحبه‌کننده خود مرور کنید تا هر دو در یک صفحه باشید.

### مرحله ۲ - ارائه طراحی سطح بالا و جلب موافقت

در این بخش، نقاط پایانی API (API endpoints)، هدایت URL و جریان‌های کوتاه‌سازی URL را بحث می‌کنیم.

#### نقاط پایانی API

نقاط پایانی API ارتباط بین کلاینت‌ها و سرورها را تسهیل می‌کنند. ما APIها را به سبک REST طراحی خواهیم کرد. یک کوتاه‌کننده URL در درجه اول به دو نقطه پایانی API نیاز دارد.

1. **کوتاه‌سازی URL:** برای ایجاد یک URL کوتاه جدید، کلاینت یک درخواست POST ارسال می‌کند که حاوی یک پارامتر است: URL بلند اصلی. API به این شکل است:
   - `POST api/v1/data/shorten`
   - پارامتر درخواست: `{longUrl: longURLString}`
   - بازگشت: `shortURL`

2. **هدایت URL:** برای هدایت یک URL کوتاه به URL بلند متناظر، کلاینت یک درخواست GET ارسال می‌کند. API به این شکل است:
   - `GET api/v1/shortUrl`
   - بازگشت: `longURL` برای هدایت HTTP

#### هدایت URL (URL redirecting)

شکل ۸-۱ نشان می‌دهد که وقتی یک tinyurl را در مرورگر وارد می‌کنید، چه اتفاقی می‌افتد. هنگامی که سرور یک درخواست tinyurl دریافت می‌کند، URL کوتاه را با هدایت ۳۰۱ به URL بلند تغییر می‌دهد.

یک نکته قابل بحث در اینجا، **هدایت ۳۰۱ در مقابل هدایت ۳۰۲** است:

- **۳۰۱ redirect:** نشان می‌دهد که URL درخواست‌شده به طور «دائم» به URL بلند منتقل شده است. از آنجا که به طور دائم هدایت می‌شود، مرورگر پاسخ را ذخیره (cache) می‌کند و درخواست‌های بعدی برای همان URL به سرویس کوتاه‌کننده URL ارسال نمی‌شوند. در عوض، درخواست‌ها مستقیماً به سرور URL بلند هدایت می‌شوند.

- **۳۰۲ redirect:** به این معنی است که URL به طور «موقت» به URL بلند منتقل شده است، به این معنی که درخواست‌های بعدی برای همان URL ابتدا به سرویس کوتاه‌کننده URL ارسال می‌شوند. سپس، به سرور URL بلند هدایت می‌شوند.

هر روش هدایت مزایا و معایب خود را دارد. اگر اولویت کاهش بار سرور است، استفاده از ۳۰۱ منطقی است زیرا فقط اولین درخواست از همان URL به سرورهای کوتاه‌کننده URL ارسال می‌شود. با این حال، اگر تحلیل (analytics) مهم است، ۳۰۲ انتخاب بهتری است زیرا می‌تواند نرخ کلیک و منبع کلیک را راحت‌تر ردیابی کند.

ساده‌ترین روش برای پیاده‌سازی هدایت URL، استفاده از **جدول درهم‌ساز (hash table)** است. با فرض اینکه جدول درهم‌ساز جفت‌های <shortURL, longURL> را ذخیره می‌کند، هدایت URL می‌تواند به صورت زیر پیاده‌سازی شود:
- دریافت longURL: `longURL = hashTable.get(shortURL)`
- پس از دریافت longURL، هدایت URL را انجام دهید.

#### کوتاه‌سازی URL (URL shortening)

فرض کنید URL کوتاه به این شکل است: `www.tinyurl.com/{hashValue}`. برای پشتیبانی از مورد استفاده کوتاه‌سازی URL، باید یک تابع درهم‌ساز (hash function) به نام fx پیدا کنیم که یک URL بلند را به hashValue نگاشت کند، همانطور که در شکل ۸-۳ نشان داده شده است.

تابع درهم‌ساز (hash function) باید شرایط زیر را برآورده کند:

- هر longURL باید به یک hashValue درهم‌سازی شود.
- هر hashValue باید بتواند دوباره به longURL نگاشت شود.

طراحی دقیق برای تابع درهم‌ساز در بخش عمیق (deep dive) بحث شده است.

### مرحله ۳ - طراحی عمیق (Deep dive)

تا اینجا، طراحی سطح بالای کوتاه‌سازی URL و هدایت URL را بحث کرده‌ایم. در این بخش، به موارد زیر عمیق‌تر می‌پردازیم: مدل داده، تابع درهم‌ساز، کوتاه‌سازی URL و هدایت URL.

#### مدل داده (Data model)

در طراحی سطح بالا، همه چیز در یک جدول درهم‌ساز (hash table) ذخیره می‌شد. این نقطه شروع خوبی است؛ با این حال، این رویکرد برای سیستم‌های دنیای واقعی به دلیل محدود و گران بودن منابع حافظه، قابل اجرا نیست. گزینه بهتر، ذخیره نگاشت <shortURL, longURL> در یک پایگاه‌داده رابطه‌ای (relational database) است. شکل ۸-۴ یک طراحی ساده جدول پایگاه‌داده را نشان می‌دهد. نسخه ساده‌شده جدول شامل ۳ ستون است: id، shortURL، longURL.

#### تابع درهم‌ساز (Hash function)

از تابع درهم‌ساز برای درهم‌سازی یک URL بلند به یک URL کوتاه، همچنین known به عنوان hashValue، استفاده می‌شود.

**طول مقدار درهم‌ساز (Hash value length)**

hashValue از کاراکترهای [0-9, a-z, A-Z] تشکیل شده است که شامل ۱۰ + ۲۶ + ۲۶ = ۶۲ کاراکتر ممکن می‌شود. برای تعیین طول hashValue، کوچکترین n را پیدا کنید به طوری که ۶۲^n ≥ ۳۶۵ میلیارد. سیستم باید بر اساس تخمین پشت پاکت، تا ۳۶۵ میلیارد URL را پشتیبانی کند. جدول ۸-۱ طول hashValue و حداکثر تعداد URLهای قابل پشتیبانی متناظر را نشان می‌دهد.

وقتی n = 7 باشد، ۶۲^۷ = حدود ۳.۵ تریلیون، ۳.۵ تریلیون برای نگهداری ۳۶۵ میلیارد URL بیش از حد کافی است، بنابراین طول hashValue برابر با ۷ است.

ما دو نوع تابع درهم‌ساز را برای کوتاه‌کننده URL بررسی خواهیم کرد. اولی **«درهم‌سازی + حل برخورد» (hash + collision resolution)** و دومی **«تبدیل پایه ۶۲» (base 62 conversion)** است. بیایید یکی یکی آن‌ها را بررسی کنیم.

#### درهم‌سازی + حل برخورد

برای کوتاه کردن یک URL بلند، باید یک تابع درهم‌ساز پیاده‌سازی کنیم که یک URL بلند را به یک رشته ۷ کاراکتری درهم‌سازی کند. یک راه‌حل ساده استفاده از توابع درهم‌ساز شناخته شده مانند CRC32، MD5 یا SHA-1 است. جدول زیر نتایج درهم‌سازی را پس از اعمال توابع مختلف درهم‌ساز روی این URL مقایسه می‌کند: `https://en.wikipedia.org/wiki/Systems_design`

همانطور که در جدول ۸-۲ نشان داده شده است، حتی کوتاه‌ترین مقدار درهم‌ساز (از CRC32) نیز خیلی بلند است (بیش از ۷ کاراکتر). چگونه می‌توانیم آن را کوتاه‌تر کنیم؟

رویکرد اول این است که ۷ کاراکتر اول یک مقدار درهم‌ساز را برداریم؛ با این حال، این روش می‌تواند منجر به برخورد درهم‌ساز (hash collision) شود. برای حل برخوردهای درهم‌ساز، می‌توانیم به طور بازگشتی (recursively) یک رشته از پیش تعریف‌شده جدید اضافه کنیم تا زمانی که دیگر برخوردی کشف نشود. این فرآیند در شکل ۸-۵ توضیح داده شده است.

این روش می‌تواند برخورد را حذف کند؛ با این حال، پرس و جو از پایگاه‌داده برای بررسی وجود shortURL برای هر درخواست، پرهزینه است. تکنیکی به نام **فیلتر بلوم (Bloom filter)** [2] می‌تواند عملکرد را بهبود بخشد. فیلتر بلوم یک تکنیک احتمالی کارآمد از نظر فضا است که برای آزمایش عضویت یک عنصر در یک مجموعه استفاده می‌شود.

#### تبدیل پایه ۶۲ (Base 62 conversion)

تبدیل پایه، رویکرد دیگری است که معمولاً برای کوتاه‌کننده‌های URL استفاده می‌شود. تبدیل پایه به تبدیل یک عدد بین سیستم‌های نمایش عددی مختلف آن کمک می‌کند. از تبدیل پایه ۶۲ استفاده می‌شود زیرا ۶۲ کاراکتر ممکن برای hashValue وجود دارد. بیایید با یک مثال توضیح دهیم که تبدیل چگونه کار می‌کند: تبدیل ۱۱۱۵۷ در سیستم پایه ۱۰ به نمایش base 62.

- از نام آن، پایه ۶۲ روشی برای استفاده از ۶۲ کاراکتر برای رمزگذاری (encoding) است. نگاشت‌ها عبارتند از: ۰-۰، ...، ۹-۹، ۱۰-a، ۱۱-b، ...، ۳۵-z، ۳۶-A، ...، ۶۱-Z، که در آن 'a' به معنای ۱۰، 'Z' به معنای ۶۱ و غیره است.
- ۱۱۱۵۷ = ۲ × ۶۲^۲ + ۵۵ × ۶۲^۱ + ۵۹ × ۶۲^۰ = [2, 55, 59] -> [2, T, X] در نمایش base 62. شکل ۸-۶ فرآیند تبدیل را نشان می‌دهد.
- بنابراین، URL کوتاه به این صورت است: `https://tinyurl.com/2TX`

#### مقایسه دو رویکرد

جدول ۸-۳ تفاوت‌های دو رویکرد را نشان می‌دهد.
### طراحی عمیق کوتاه‌سازی URL

به عنوان یکی از بخش‌های اصلی سیستم، می‌خواهیم جریان کوتاه‌سازی URL از نظر منطقی ساده و کاربردی باشد. از تبدیل پایه ۶۲ در طراحی ما استفاده شده است. نمودار زیر (شکل ۸-۷) را برای نمایش جریان کار می‌سازیم.

1. **longURL** ورودی است.
2. سیستم بررسی می‌کند که آیا longURL در پایگاه‌داده وجود دارد یا خیر.
3. اگر وجود داشته باشد، به این معناست که longURL قبلاً به shortURL تبدیل شده است. در این حالت، shortURL را از پایگاه‌داده دریافت کرده و به کلاینت بازگردانید.
4. اگر وجود نداشته باشد، longURL جدید است. یک شناسه یکتا (کلید اصلی) جدید توسط تولیدکننده شناسه یکتا (unique ID generator) تولید می‌شود.
5. شناسه را با استفاده از تبدیل پایه ۶۲ به shortURL تبدیل کنید.
6. یک ردیف جدید پایگاه‌داده با شناسه، shortURL و longURL ایجاد کنید.

برای درک آسان‌تر جریان، بیایید به یک مثال مشخص نگاه کنیم:

- فرض کنید longURL ورودی این است: `https://en.wikipedia.org/wiki/Systems_design`
- تولیدکننده شناسه یکتا، شناسه زیر را برمی‌گرداند: **2009215674938**
- شناسه را با استفاده از تبدیل پایه ۶۲ به shortURL تبدیل کنید. شناسه (2009215674938) به "zn9edcu" تبدیل می‌شود.
- شناسه، shortURL و longURL را در پایگاه‌داده ذخیره کنید، همانطور که در جدول ۸-۴ نشان داده شده است.

تولیدکننده شناسه یکتا توزیع‌شده قابل ذکر است. وظیفه اصلی آن تولید شناسه‌های جهانی یکتا (globally unique) است که برای ایجاد shortURLها استفاده می‌شود. در یک محیط بسیار توزیع‌شده، پیاده‌سازی یک تولیدکننده شناسه یکتا چالش‌برانگیز است. خوشبختانه، ما قبلاً چندین راه‌حل را در «فصل ۷: طراحی یک تولیدکننده شناسه یکتا در سیستم‌های توزیع‌شده» بحث کرده‌ایم. می‌توانید برای تازه کردن حافظه خود به آن مراجعه کنید.

### طراحی عمیق هدایت URL (URL redirecting)

شکل ۸-۸ طراحی دقیق هدایت URL را نشان می‌دهد. از آنجا که تعداد خواندن‌ها بیشتر از نوشتن‌ها است، نگاشت <shortURL, longURL> در حافظه پنهان (cache) ذخیره می‌شود تا عملکرد بهبود یابد.

جریان هدایت URL به شرح زیر خلاصه می‌شود:

1. کاربر روی یک لینک URL کوتاه کلیک می‌کند: `https://tinyurl.com/zn9edcu`
2. توزیع‌کننده بار (load balancer) درخواست را به سرورهای وب (web servers) هدایت می‌کند.
3. اگر shortURL از قبل در حافظه پنهان وجود داشته باشد، longURL را مستقیماً بازگردانید.
4. اگر shortURL در حافظه پنهان نباشد، longURL را از پایگاه‌داده دریافت کنید. اگر در پایگاه‌داده نباشد، احتمالاً کاربر یک shortURL نامعتبر وارد کرده است.
5. longURL به کاربر بازگردانده می‌شود.

### مرحله ۴ - جمع‌بندی

در این فصل، درباره طراحی API، مدل داده، تابع درهم‌ساز، کوتاه‌سازی URL و هدایت URL صحبت کردیم.

اگر در پایان مصاحبه زمان اضافی داشتید، در اینجا چند نکته بحث اضافی آورده شده است:

- **محدودکننده نرخ (Rate limiter):** یک مشکل امنیتی بالقوه که می‌توانیم با آن مواجه شویم این است که کاربران مخرب تعداد بسیار زیادی درخواست کوتاه‌سازی URL ارسال می‌کنند. محدودکننده نرخ به فیلتر کردن درخواست‌ها بر اساس آدرس IP یا سایر قوانین فیلترینگ کمک می‌کند. اگر می‌خواهید حافظه خود را در مورد محدودکننده نرخ تازه کنید، به «فصل ۴: طراحی یک محدودکننده نرخ» مراجعه کنید.

- **مقیاس‌پذیری سرور وب (Web server scaling):** از آنجا که لایه وب بدون حالت (stateless) است، مقیاس‌پذیری لایه وب با افزودن یا حذف سرورهای وب آسان است.

- **مقیاس‌پذیری پایگاه‌داده (Database scaling):** تکثیر پایگاه‌داده (replication) و شاردینگ (sharding) تکنیک‌های رایج هستند.

- **تحلیل (Analytics):** داده برای موفقیت کسب‌وکار به طور فزاینده‌ای مهم است. ادغام یک راه‌حل تحلیلی با کوتاه‌کننده URL می‌تواند به پاسخ به سؤالات مهمی مانند: چند نفر روی یک لینک کلیک می‌کنند؟ چه زمانی روی لینک کلیک می‌کنند؟ و غیره کمک کند.

- **در دسترس بودن، سازگاری و قابلیت اطمینان (Availability, consistency, reliability):** این مفاهیم در هسته موفقیت هر سیستم بزرگی قرار دارند. ما در فصل ۱ به تفصیل درباره آنها بحث کردیم، لطفاً حافظه خود را در مورد این موضوعات تازه کنید.
