## وابستگی چرخشی (Cyclic Dependencies): دشمن خاموش ماژولاریتی

🔍 **ماژولاریتی** یک ویژگی معماری **ضمنی (implicit)** و کلیدی است که اکثر معماران نرم‌افزار به آن حساس هستند. ساختار ضعیف و درهم‌تنیده ماژول‌ها می‌تواند به سرعت کیفیت کد و معماری را به خطر بیندازد. به همین دلیل، معماران تلاش می‌کنند **ماژولاریتی سالم و مستقل** را حفظ کنند.

اما مشکل کجاست؟

در عمل، اغلب **نیروهای مخربی در سکوت علیه این هدف حرکت می‌کنند.**

---

## IDE و Auto-Import: دشمنی که لبخند می‌زند

در اغلب IDEهای محبوب مانند IntelliJ، Eclipse یا Visual Studio، زمانی‌که یک کلاس از ماژول دیگر استفاده می‌شود، ابزار توسعه خیلی "مفید" عمل می‌کند:

> 💡 «آیا مایل هستید این کلاس را import کنیم؟»

و این پیشنهاد آنقدر تکرار می‌شود که برای بسیاری از برنامه‌نویسان به یک **واکنش رفلکسی** تبدیل شده است.

اما مشکل اینجاست:

هر import خودسرانه می‌تواند شروع یک **وابستگی دوطرفه یا حلقه‌ای** باشد، که مانند یک سرطان در معماری گسترش پیدا می‌کند.

---

## الگوی ضدمعماری: حلقه‌های وابستگی

در شکل زیر (از کتاب)، سه کامپوننت داریم که هرکدام به دیگری وابسته‌اند. نتیجه این است که **هیچ‌کدام مستقل نیستند** و نمی‌توانند جداگانه استفاده یا تست شوند:

```
Web  <-->  Service  <-->  Persistence  <-->  Web
```

این الگو پایه‌گذار چیزی است که در ادبیات معماری به آن می‌گوییم:

> 🎯 **Big Ball of Mud** — توپ گل آلود معماری

در این وضعیت:

* امکان تست جداگانه حذف می‌شود
* Deployment مستقل غیرممکن می‌شود
* تغییر در یک قسمت باعث رگرشن در چندین نقطه می‌شود
* و در نهایت معماری **فرو می‌پاشد**

---

## راه‌حل حرفه‌ای: Fitness Function برای کنترل حلقه‌ها

کد زیر مثالی از یک **Fitness Function اتوماتیک** برای جلوگیری از ایجاد حلقه‌های وابستگی بین packageهای Java است. ابزار مورد استفاده: [`JDepend`](https://github.com/clarkware/jdepend)

```java
public class CycleTest {
  private JDepend jdepend;

  @BeforeEach
  void init() {
    jdepend = new JDepend();
    jdepend.addDirectory("/path/to/project/persistence/classes");
    jdepend.addDirectory("/path/to/project/web/classes");
    jdepend.addDirectory("/path/to/project/thirdpartyjars");
  }

  @Test
  void testAllPackages() {
    Collection packages = jdepend.analyze();
    assertEquals("Cycles exist", false, jdepend.containsCycles());
  }
}
```

### توضیح:

* تست بالا ساختار packageها را تحلیل می‌کند
* اگر **وابستگی چرخشی** وجود داشته باشد، تست fail می‌شود
* می‌توان این تست را در لوله CI/CD قرار داد تا تغییرات معماری درجا مسدود شوند

---

## نکته حیاتی

این تست یک نمونه عالی از **“مراقبت از موارد مهم به‌جای موارد فوری”** در معماری است.

* توسعه‌دهنده ممکن است با هدف تحویل سریع، وابستگی ایجاد کند
* اما معمار باید مراقب باشد **ساختار کل سیستم تخریب نشود**
* با Fitness Function، معمار نیازی به بررسی دستی هر تغییر ندارد

## جمع‌بندی

🛑 **وابستگی چرخشی دشمن شماره یک ماژولاریتی است.**

✅ معمار باید به کمک ابزارهایی مانند JDepend، SonarQube یا ArchUnit یک خط دفاعی خودکار بسازد.

⚙️ این کار یک مثال عملی از **Governance در معماری مدرن** است.

نه فقط با مستندات و توصیه‌ها، بلکه با کد قابل اجرا که از سلامت ساختار دفاع می‌کند.
