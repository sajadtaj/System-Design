# فصل ۲ - معماری Celery، Redis و Django

## اهداف یادگیری

در پایان این فصل خواهید توانست:

* معماری Celery را درک کنید.
* نقش هر یک از اجزای اصلی سیستم را توضیح دهید.
* ارتباط بین Django، Redis و Worker را تحلیل کنید.
* مسیر حرکت یک Task را از ایجاد تا اجرا دنبال کنید.

---

# مقدمه

در فصل قبل با مفهوم پردازش ناهمگام آشنا شدیم و دیدیم که چرا اجرای مستقیم عملیات زمان‌بر در یک View مناسب نیست.

اکنون سؤال مهم‌تری مطرح می‌شود.

وقتی در Django یک Task ایجاد می‌کنیم، این Task دقیقاً به کجا می‌رود؟

چه چیزی آن را اجرا می‌کند؟

Redis چه نقشی دارد؟

Worker چگونه متوجه می‌شود که Task جدیدی ایجاد شده است؟

پاسخ تمام این پرسش‌ها در معماری Celery نهفته است.

# سناریوی واقعی

کاربر وارد سامانه مدیریت صندوق می‌شود.

روی دکمه **به‌روزرسانی اطلاعات بازار** کلیک می‌کند.

در ظاهر تنها یک درخواست HTTP ارسال می‌شود.

اما در پشت صحنه چندین مؤلفه با یکدیگر همکاری می‌کنند تا این عملیات بدون اشغال کردن درخواست کاربر انجام شود.

# اجزای اصلی معماری

## Django

Django نقطه ورود درخواست‌های کاربران است.

کاربران هرگز مستقیماً با Celery ارتباط برقرار نمی‌کنند.

Django تنها مسئول ایجاد Task است.

اجرای Task وظیفه Django نیست.

---

## Celery

Celery یک سیستم مدیریت Task است.

وظیفه Celery این است که:

* Taskها را ثبت کند.
* آن‌ها را در صف قرار دهد.
* اجرای آن‌ها را به Workerها واگذار کند.

Celery هیچ وابستگی مستقیمی به Django ندارد و می‌تواند در پروژه‌های غیر Django نیز استفاده شود.

---

## Redis

در این کتاب Redis به عنوان **Message Broker** استفاده خواهد شد.

وظیفه Redis تنها انتقال پیام است.

وقتی Django یک Task ایجاد می‌کند، اطلاعات آن در Redis قرار می‌گیرد.

Redis منتظر می‌ماند تا یکی از Workerها پیام را دریافت کند.

بنابراین Redis محل اجرای Task نیست.

---

## Worker

Worker یک پردازش مستقل از Django است.

این پردازش دائماً Redis را بررسی می‌کند.

به محض مشاهده یک Task جدید، آن را دریافت و اجرا می‌کند.

اگر Worker اجرا نشود، هیچ Taskی پردازش نخواهد شد.

---

## پایگاه داده

پس از پایان عملیات، Worker می‌تواند داده‌ها را در PostgreSQL ذخیره کند.

در این مرحله دیگر هیچ ارتباطی با درخواست اولیه کاربر وجود ندارد.

---

# مسیر حرکت یک Task

در ادامه مسیر کامل اجرای یک Task را مشاهده می‌کنیم.

```text
کاربر

      │

      ▼

ارسال درخواست HTTP

      │

      ▼

Django

      │

      ▼

      ▼

      │

      │

      │

```

این چرخه اساس تمام پروژه‌هایی است که با Celery توسعه داده می‌شوند.

---

# چرا Worker جدا از Django اجرا می‌شود؟

فرض کنید عملیات دریافت اطلاعات بازار ۲۰ ثانیه طول بکشد.

اگر Django این عملیات را انجام دهد، Thread مربوط به درخواست تا پایان عملیات اشغال خواهد شد.

اما وقتی Worker این عملیات را انجام دهد:

* Django بلافاصله پاسخ HTTP را ارسال می‌کند.
* Worker در پس‌زمینه عملیات را ادامه می‌دهد.
* کاربران دیگر تحت تأثیر این پردازش قرار نمی‌گیرند.

---

# آیا همیشه Redis لازم است؟

خیر.

Celery از Brokerهای مختلفی پشتیبانی می‌کند.

از جمله:

* Redis
* RabbitMQ

در این کتاب Redis انتخاب شده است زیرا:

* نصب ساده‌تری دارد.
* برای اکثر پروژه‌های Django مناسب است.
* در پروژه‌های کوچک و متوسط عملکرد بسیار خوبی دارد.

---

# بهترین شیوه‌ها

* Worker را مستقل از Django اجرا کنید.
* از Redis تنها به عنوان Broker استفاده کنید.
* منطق تجاری را داخل Worker قرار دهید، نه در Viewها.
* قبل از نوشتن اولین Task، معماری سیستم را به خوبی درک کنید.
