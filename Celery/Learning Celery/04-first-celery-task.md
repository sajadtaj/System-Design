# فصل ۴ - ایجاد اولین Task در Celery

## اهداف یادگیری

در پایان این فصل خواهید توانست:

- مفهوم Task را در Celery به‌درستی درک کنید.
- تفاوت اجرای همگام (Synchronous) و ناهمگام (Asynchronous) را در سطح کد مشاهده کنید.
- اولین فایل `tasks.py` را ایجاد کنید.
- اولین Task پروژه را با استفاده از `@shared_task` بنویسید.

- نتیجه اجرای Task را بررسی کنید.

# سناریوی واقعی

فرض کنید سامانه مالی شما باید هر زمان کاربر درخواست کرد، آخرین قیمت بیت‌کوین را از یک API عمومی دریافت کند.

در نگاه اول شاید چنین کدی بنویسیم.

```python
price = get_bitcoin_price()
```

اما این روش یک مشکل اساسی دارد.

تا زمانی که پاسخ API دریافت نشود، Thread مربوط به درخواست کاربر نیز متوقف خواهد ماند.

اگر پاسخ API پنج ثانیه طول بکشد، کاربر نیز پنج ثانیه منتظر خواهد ماند.

در سامانه‌های مالی، چنین رفتاری قابل قبول نیست.

راه‌حل، واگذاری این عملیات به Celery است.

---

# Task چیست؟

Task کوچک‌ترین واحد کاری در Celery است.

هر عملیاتی که بتوان آن را مستقل از درخواست کاربر اجرا کرد، یک Task محسوب می‌شود.

برای مثال:

- دریافت اطلاعات از یک API
- ارسال ایمیل
- تولید گزارش
- پردازش تصویر
- محاسبات سنگین
- همگام‌سازی داده‌ها
- پاک‌سازی اطلاعات قدیمی

در این کتاب، تمرکز اصلی ما روی **دریافت و پردازش داده‌های مالی** خواهد بود.

---

# یک Task چه ویژگی‌هایی دارد؟

یک Task مناسب باید ویژگی‌های زیر را داشته باشد:

- مستقل باشد.
- ورودی و خروجی مشخصی داشته باشد.
- در صورت شکست، امکان اجرای مجدد (Retry) داشته باشد.
- تا حد امکان بدون وابستگی به وضعیت درخواست کاربر باشد.
- اجرای آن زمان‌بر یا پردازش‌محور باشد.

هرچه یک Task کوچک‌تر و متمرکزتر باشد، نگهداری و آزمایش آن ساده‌تر خواهد بود.

---

# چرا از مثال‌های ساده استفاده نمی‌کنیم؟

در بسیاری از آموزش‌ها اولین Task به شکل زیر است.

```python
@shared_task
def add(x, y):
    return x + y
```

این مثال برای آشنایی اولیه مناسب است، اما تقریباً هیچ شباهتی به پروژه‌های واقعی ندارد.

در این کتاب از همان ابتدا یک سناریوی واقعی را انتخاب می‌کنیم تا تمام قابلیت‌های Celery را روی آن توسعه دهیم.

---

# سناریوی پروژه

در طول کتاب، یک سامانه جمع‌آوری اطلاعات مالی خواهیم ساخت.

اولین Task این سامانه وظیفه دارد قیمت لحظه‌ای بیت‌کوین را از یک API عمومی دریافت کند.

در فصل‌های بعد همین Task را توسعه خواهیم داد و قابلیت‌هایی مانند Retry، Logging، Scheduling، Rate Limiting و Monitoring را به آن اضافه خواهیم کرد.

به این ترتیب، به جای یادگیری مجموعه‌ای از مثال‌های پراکنده، یک پروژه واقعی را مرحله‌به‌مرحله تکمیل خواهیم کرد.

---

# چرا بیت‌کوین؟

انتخاب بیت‌کوین صرفاً به دلیل محبوبیت آن نیست.

این مثال چند مزیت مهم دارد:

- داده‌ها به‌صورت عمومی در دسترس هستند.
- نیازی به احراز هویت نیست.
- تغییرات قیمت واقعی و پویا هستند.
- پاسخ API ساختار مشخصی دارد.
- در فصل‌های بعد می‌توان انواع خطاها، Retry و زمان‌بندی را روی آن پیاده‌سازی کرد.

بنابراین این مثال تقریباً تمام نیازهای آموزشی کتاب را پوشش می‌دهد.

---

# معماری اجرای اولین Task

در این فصل برای اولین بار مسیر کامل اجرای یک Task را مشاهده خواهیم کرد.

```text
             Django

                │

                ▼

      ارسال Task به Redis

                │

                ▼

                │

                ▼

                │

                ▼

                │

                ▼

```

در فصل سوم تنها زیرساخت این مسیر را ایجاد کردیم.

در این فصل، این مسیر برای اولین بار به‌صورت عملی طی خواهد شد.

# گام اول - محل قرارگیری Taskها

یکی از اولین سؤال‌هایی که هنگام کار با Celery مطرح می‌شود این است:

> Taskها را در کدام فایل قرار دهیم؟

پاسخ این سؤال در پروژه‌های Django بسیار ساده است.

هر برنامه (Application) می‌تواند فایل مستقلی به نام `tasks.py` داشته باشد.

برای مثال اگر ساختار پروژه به شکل زیر باشد:

```text
financial-data-collector/

├── config/
│
├── market/
│   ├── models.py
│   ├── views.py
│   ├── services.py
│   ├── tasks.py
│   └── ...
│
└── manage.py
```

تمام Taskهای مربوط به برنامه `market` داخل فایل زیر قرار خواهند گرفت.

```text
market/tasks.py
```

این همان ساختاری است که مستندات رسمی Django و Celery نیز پیشنهاد می‌کنند.

# چرا همه Taskها را در یک فایل قرار نمی‌دهیم؟

گاهی در پروژه‌های کوچک مشاهده می‌شود که تمام Taskها در یک فایل مانند زیر نوشته می‌شوند.

```text
tasks.py
```

در نگاه اول این روش ساده به نظر می‌رسد، اما با رشد پروژه مشکلات زیادی ایجاد می‌کند.

برای مثال:

- یافتن Taskها دشوار می‌شود.
- وابستگی بین بخش‌های مختلف افزایش پیدا می‌کند.
- استفاده مجدد از برنامه‌ها (Reusable Apps) سخت‌تر می‌شود.
- تست‌نویسی پیچیده‌تر خواهد شد.

به همین دلیل، هر App باید فایل `tasks.py` مخصوص خود را داشته باشد.

# اولین Task

در ابتدا ساده‌ترین نسخه Task را ایجاد می‌کنیم.

```python
from celery import shared_task


@shared_task
def fetch_bitcoin_price():
    """
    Fetch the latest Bitcoin price.

    This is a placeholder task.
    The implementation will be completed
    in the next sections.
    """

    return "Task executed successfully."
```

فعلاً این Task هیچ APIای را فراخوانی نمی‌کند.

هدف ما در این بخش تنها این است که مطمئن شویم:

- Django فایل را شناسایی می‌کند.
- Celery فایل را Import می‌کند.
- Worker می‌تواند Task را ثبت کند.
- Task بدون خطا اجرا می‌شود.

در بخش‌های بعدی، این Task را به یک Task واقعی تبدیل خواهیم کرد.

---

# چرا از `@shared_task` استفاده می‌کنیم؟

مهم‌ترین تصمیم این فصل، انتخاب دکوراتور مناسب است.

Celery دو روش رایج برای تعریف Task ارائه می‌کند.

روش اول:

```python
@app.task
def my_task():
    ...
```

روش دوم:

```python
@shared_task
def my_task():
    ...
```

در پروژه‌های Django تقریباً همیشه روش دوم توصیه می‌شود.

---

# مزایای `shared_task`

استفاده از `shared_task` چند مزیت مهم دارد.

## وابستگی کمتر

Task مستقیماً به شیء `Celery App` وابسته نیست.

در نتیجه برنامه قابلیت استفاده مجدد خواهد داشت.

---

## سازگاری با Django

مستندات رسمی Celery برای برنامه‌های Django استفاده از `shared_task` را توصیه می‌کنند.

به همین دلیل تقریباً تمام پروژه‌های متن‌باز Django نیز از همین روش استفاده می‌کنند.

---

## قابلیت انتقال

فرض کنید در آینده بخواهید App `market` را به پروژه دیگری منتقل کنید.

اگر تمام Taskها با `shared_task` نوشته شده باشند، معمولاً بدون تغییر قابل استفاده خواهند بود.

---

# فرآیند ثبت یک Task

زمانی که Worker اجرا می‌شود، اتفاقات زیر رخ می‌دهد.

```text
Worker

      │

      ▼

autodiscover_tasks()

      │

      ▼

INSTALLED_APPS

      │

      ▼

market

      │

      ▼

tasks.py

      │

      ▼

@shared_task

      │

      ▼

ثبت Task
```

به همین دلیل در فصل سوم از دستور زیر استفاده کردیم.

```python
app.autodiscover_tasks()
```

اگر این دستور حذف شود، Worker فایل `tasks.py` را پیدا نخواهد کرد و هیچ Taskی ثبت نمی‌شود.

---

# آیا لازم است Task را Import کنیم؟

خیر.

این یکی از مزایای مهم Celery است.

پس از ایجاد فایل `tasks.py`، تنها کافی است Worker را مجدداً اجرا کنید.

```bash
celery -A config worker --loglevel=INFO
```

در زمان راه‌اندازی، Celery به‌صورت خودکار فایل را شناسایی و Import خواهد کرد.

به همین دلیل در اکثر پروژه‌ها هیچ Import دستی برای Taskها مشاهده نمی‌شود.

---

# وضعیت پروژه

در پایان این بخش:

- فایل `tasks.py` ایجاد شده است.
- اولین Task پروژه نوشته شده است.
- Worker قادر به شناسایی Task خواهد بود.

اما هنوز Task را اجرا نکرده‌ایم.

در بخش بعدی برای نخستین بار Task را از داخل Django به Redis ارسال خواهیم کرد و اجرای آن را در Worker مشاهده خواهیم نمود.

اکنون فایل زیر را ایجاد کنید.

## فایل

**مسیر**


**وضعیت**

ایجاد فایل جدید

---

### کد

```python
from celery import shared_task


@shared_task
def fetch_bitcoin_price():
    """
    Fetch the latest Bitcoin price.
    """

    print("Fetching Bitcoin price...")

    return "OK"
```

---

# تحلیل کد

در نگاه اول، این تابع بسیار ساده است؛ اما تمام اجزای اصلی یک Task را در خود دارد.

---

## دکوراتور `@shared_task`

```python
@shared_task
```

این دکوراتور تابع معمولی پایتون را به یک Task قابل اجرا توسط Celery تبدیل می‌کند.

در زمان راه‌اندازی Worker، Celery تمام توابعی را که با این دکوراتور مشخص شده‌اند ثبت می‌کند.

---

## بدنه تابع

```python
def fetch_bitcoin_price():
```

در حال حاضر تابع هیچ ورودی دریافت نمی‌کند.

در فصل‌های بعد، پارامترهایی مانند نماد (Symbol)، بازار (Market) و Provider را به آن اضافه خواهیم کرد.

فعلاً هدف ما تنها اطمینان از صحت اجرای زیرساخت است.

---

## مقدار بازگشتی

```python
return "OK"
```

هر Task می‌تواند مقداری را به Result Backend بازگرداند.

در این فصل مقدار `"OK"` صرفاً برای آزمایش استفاده می‌شود.

در فصل‌های آینده، این مقدار به داده‌های واقعی API تبدیل خواهد شد.

# راه‌اندازی مجدد Worker

اگر Worker از قبل در حال اجرا است، آن را متوقف کنید.

```text
Ctrl + C
```

سپس دوباره اجرا کنید.

```bash
celery -A config worker --loglevel=INFO
```

# بررسی ثبت Task

در خروجی Worker اکنون باید بخش `[tasks]` دیگر خالی نباشد.

نمونه خروجی:

```text
[tasks]

  . market.tasks.fetch_bitcoin_price
```

نمایش این نام، به این معنی است که:

- فایل `tasks.py` پیدا شده است.
- تابع Import شده است.
- دکوراتور `@shared_task` به‌درستی عمل کرده است.
- Task با موفقیت در Worker ثبت شده است.

این مرحله یکی از مهم‌ترین نقاط عطف پروژه است؛ زیرا از این لحظه، زیرساخت Celery آماده اجرای Taskهای واقعی است.

---

# آیا Task اجرا شده است؟

خیر.

نکته مهمی که بسیاری از توسعه‌دهندگان در ابتدای کار با Celery با آن اشتباه می‌کنند این است که:

ثبت شدن (Registration) با اجرا شدن (Execution) تفاوت دارد.

در این مرحله فقط Worker از وجود Task مطلع شده است.

هنوز هیچ درخواستی برای اجرای آن ارسال نشده است.

در بخش بعدی، برای نخستین بار از داخل Django یک Task را به صف Redis ارسال می‌کنیم و اجرای آن را به‌صورت زنده در Worker مشاهده خواهیم کرد.

---
