# فصل ۳ - راه‌اندازی Celery در پروژه Django

## اهداف یادگیری

در پایان این فصل خواهید توانست:

* Celery را به یک پروژه Django اضافه کنید.

# سناریوی واقعی

تا اینجا معماری پروژه را طراحی کرده‌ایم، اما هنوز هیچ زیرساختی برای اجرای Taskها وجود ندارد.

فرض کنید مدیر محصول از شما درخواست می‌کند که در نسخه بعدی سامانه، دریافت اطلاعات بازار به‌صورت پس‌زمینه انجام شود.

در این لحظه، اولین سؤال یک توسعه‌دهنده این نیست که «چگونه Task بنویسم؟»

بلکه باید بپرسد:

> **چگونه Django را برای استفاده از Celery آماده کنم؟**

اگر این زیرساخت به‌درستی طراحی نشود، در ادامه پروژه با مشکلاتی مانند ثبت نشدن Taskها، شناسایی نشدن Workerها یا وابستگی شدید بین اجزای سیستم روبه‌رو خواهیم شد.

به همین دلیل، در این فصل تنها روی آماده‌سازی زیرساخت تمرکز می‌کنیم.

# گام اول - نصب Celery

ابتدا محیط مجازی پروژه را فعال کنید.

سپس Celery را نصب نمایید.

```bash
pip install celery
```

برای اطمینان از نصب صحیح، نسخه Celery را بررسی کنید.

```bash
celery --version
```

نمونه خروجی:

```text

```

در زمان نگارش این کتاب، تمام مثال‌ها بر اساس شاخه 5.x نوشته شده‌اند.

# Celery دقیقاً چه چیزی را نصب می‌کند؟

بسیاری از توسعه‌دهندگان تصور می‌کنند Celery تنها یک کتابخانه برای اجرای Taskها است.

در واقع، Celery مجموعه‌ای از قابلیت‌های زیر را در اختیار پروژه قرار می‌دهد:

* مدیریت صف وظایف (Task Queue)
* زمان‌بندی اجرای وظایف
* مدیریت Workerها
* مدیریت صف‌های مختلف
* مکانیزم Retry
* مدیریت نتایج Taskها
* ابزارهای مانیتورینگ

در این فصل تنها از بخش راه‌اندازی اولیه استفاده خواهیم کرد و سایر قابلیت‌ها در فصل‌های بعد به‌تدریج معرفی می‌شوند.

# گام دوم - نصب کتابخانه Redis

Celery برای ارتباط با Redis به کتابخانه Python مربوط به Redis نیاز دارد.

آن را نصب کنید.

```bash
pip install redis
```

پس از پایان نصب، وابستگی‌های پروژه را ثبت کنید.

```bash
pip freeze > requirements/base.txt
```

> اگر ساختار پروژه شما برای مدیریت وابستگی‌ها متفاوت است، فایل مناسب پروژه خود را به‌روزرسانی کنید. در طول کتاب فرض می‌کنیم فایل `requirements/base.txt` مرجع وابستگی‌های محیط توسعه است.

# چرا کتابخانه redis را جداگانه نصب می‌کنیم؟

Celery از Brokerهای مختلفی مانند Redis و RabbitMQ پشتیبانی می‌کند.

به همین دلیل وابستگی مربوط به Redis به‌صورت مستقل نصب می‌شود.

این طراحی باعث شده است Celery به یک Broker خاص وابسته نباشد و بتواند در معماری‌های مختلف مورد استفاده قرار گیرد.

در پروژه این کتاب، Redis تنها به عنوان **Message Broker** استفاده خواهد شد.

در فصل‌های آینده درباره Result Backend و تفاوت آن با Broker نیز صحبت خواهیم کرد.

# گام سوم - ایجاد فایل `config/celery.py`

اکنون باید نقطه ورود (Entry Point) مربوط به Celery را در پروژه ایجاد کنیم.

این فایل مسئول مقداردهی اولیه (Initialization) برنامه Celery و برقراری ارتباط آن با تنظیمات Django است.

ساختار پوشه `config` پس از این مرحله به شکل زیر خواهد بود.

```text
config/
│
├── __init__.py
├── settings.py
├── urls.py
├── asgi.py
├── wsgi.py
└── celery.py
```

---

## فایل

**مسیر**

```text
config/celery.py
```

**وضعیت**

ایجاد فایل جدید

### کد

```python
import os

from celery import Celery

os.environ.setdefault(
    "DJANGO_SETTINGS_MODULE",
    "config.settings",
)

app = Celery("config")

app.config_from_object(
    "django.conf:settings",
    namespace="CELERY",
)

app.autodiscover_tasks()
```

---

## تحلیل کد

در نگاه اول، فایل `celery.py` بسیار ساده به نظر می‌رسد؛ اما هر خط از آن نقش مهمی در راه‌اندازی Celery دارد.

در ادامه، هر بخش را جداگانه بررسی می‌کنیم.

---

### تعیین فایل تنظیمات Django

```python
os.environ.setdefault(
    "DJANGO_SETTINGS_MODULE",
    "config.settings",
)
```

Celery یک برنامه مستقل از Django است.

به همین دلیل هنگام اجرا نمی‌داند تنظیمات پروژه در کدام فایل قرار دارند.

این دستور متغیر محیطی `DJANGO_SETTINGS_MODULE` را تنظیم می‌کند تا Celery بتواند تنظیمات Django را بارگذاری کند.

اگر این بخش حذف شود، هنگام اجرای Worker با خطاهای مشابه زیر مواجه خواهید شد.

```text
django.core.exceptions.ImproperlyConfigured
```

یا

```text
Requested setting INSTALLED_APPS, but settings are not configured.
```

---

### ایجاد برنامه Celery

```python
app = Celery("config")
```

این خط، شیء اصلی Celery را ایجاد می‌کند.

از این پس، تمام Workerها، Taskها و تنظیمات پروژه به این شیء متصل خواهند شد.

پارامتر `"config"` تنها نام برنامه Celery است و معمولاً با نام پروژه یکسان انتخاب می‌شود.

---

### بارگذاری تنظیمات از Django

```python
app.config_from_object(
    "django.conf:settings",
    namespace="CELERY",
)
```

این بخش یکی از مهم‌ترین قسمت‌های فایل است.

به Celery اعلام می‌کنیم که تنظیمات خود را از فایل `settings.py` دریافت کند.

وجود پارامتر `namespace` باعث می‌شود تنها تنظیماتی خوانده شوند که با پیشوند `CELERY_` تعریف شده‌اند.

برای مثال:

```python
CELERY_BROKER_URL = ...
CELERY_RESULT_BACKEND = ...
CELERY_TIMEZONE = ...
```

اگر از `namespace` استفاده نکنیم، Celery تمام متغیرهای موجود در فایل تنظیمات را بررسی خواهد کرد که علاوه بر کاهش خوانایی، احتمال تداخل نام‌ها را نیز افزایش می‌دهد.

---

### شناسایی خودکار Taskها

```python
app.autodiscover_tasks()
```

یکی از قابلیت‌های مهم Celery، شناسایی خودکار فایل‌های `tasks.py` است.

با استفاده از این دستور، Celery تمام برنامه‌های ثبت‌شده در `INSTALLED_APPS` را بررسی می‌کند و در صورت وجود فایل `tasks.py`، آن را به‌طور خودکار بارگذاری می‌کند.

به همین دلیل در آینده نیازی به ثبت دستی Taskها نخواهیم داشت.

---

# گام چهارم - ویرایش فایل `config/__init__.py`

تا این مرحله فایل `celery.py` ایجاد شده است، اما Django هنوز از وجود آن اطلاعی ندارد.

برای حل این مسئله، فایل `config/__init__.py` را ویرایش می‌کنیم.

---

## فایل

**مسیر**

```text
config/__init__.py
```

**وضعیت**

ویرایش فایل موجود

### کد

```python
from .celery import app as celery_app

__all__ = ("celery_app",)
```

---

## چرا این فایل را ویرایش می‌کنیم؟

هنگامی که Django پروژه را بارگذاری می‌کند، فایل `config` نیز Import می‌شود.

با Import کردن `celery_app` در این مرحله، برنامه Celery نیز هم‌زمان مقداردهی اولیه خواهد شد.

در نتیجه، نیازی نیست در بخش‌های مختلف پروژه به‌صورت دستی فایل `celery.py` را Import کنیم.

این روش، همان ساختاری است که در مستندات رسمی Celery برای پروژه‌های Django توصیه شده است.

# گام پنجم - پیکربندی Celery در فایل `settings.py`

تا این مرحله، Django و Celery به یکدیگر متصل شده‌اند؛ اما Celery هنوز نمی‌داند:

* پیام‌ها را در کجا قرار دهد.
* نتایج Taskها را در کجا ذخیره کند.
* چه فرمتی برای تبادل داده‌ها استفاده شود.
* منطقه زمانی (Time Zone) پروژه چیست.

تمام این تنظیمات در فایل `settings.py` انجام می‌شود.

---

## فایل

**مسیر**

```text
config/settings.py
```

**وضعیت**

ویرایش فایل موجود

---

### کد

```python
# ------------------------------------------------------------------------------
# Celery Configuration
# ------------------------------------------------------------------------------

CELERY_BROKER_URL = "redis://127.0.0.1:6379/0"

CELERY_RESULT_BACKEND = "redis://127.0.0.1:6379/0"

CELERY_ACCEPT_CONTENT = ["json"]

CELERY_TASK_SERIALIZER = "json"

CELERY_RESULT_SERIALIZER = "json"

CELERY_TIMEZONE = TIME_ZONE
```

# تحلیل تنظیمات

در نگاه اول، این چند متغیر ساده به نظر می‌رسند، اما تقریباً تمام رفتار Celery بر اساس همین تنظیمات کنترل می‌شود.

در ادامه، هر کدام را جداگانه بررسی می‌کنیم.

---

## `CELERY_BROKER_URL`

```python
CELERY_BROKER_URL = "redis://127.0.0.1:6379/0"
```

این مهم‌ترین تنظیم Celery است.

Broker محلی است که Taskها در آن قرار می‌گیرند تا توسط Worker دریافت و اجرا شوند.

در این کتاب از Redis به عنوان Message Broker استفاده می‌کنیم.

اجزای این آدرس به صورت زیر هستند.

```text
redis://127.0.0.1:6379/0
│       │         │      │
│       │         │      └── شماره Database در Redis
│       │         └──────── پورت Redis
│       └────────────────── آدرس Redis
└────────────────────────── پروتکل ارتباطی
```

در محیط توسعه، Worker روی سیستم عامل (Host) اجرا می‌شود؛ بنابراین از آدرس `127.0.0.1` استفاده می‌کنیم.

> **نکته مهم**
>
> در فصل استقرار با Docker Compose، این مقدار به `redis://redis:6379/0` تغییر خواهد کرد؛ زیرا در آن معماری، ارتباط از طریق نام سرویس Docker برقرار می‌شود.

---

## `CELERY_RESULT_BACKEND`

```python
CELERY_RESULT_BACKEND = "redis://127.0.0.1:6379/0"
```

پس از پایان اجرای یک Task، نتیجه آن در مکانی به نام **Result Backend** ذخیره می‌شود.

در پروژه این کتاب، Redis هم نقش Message Broker و هم نقش Result Backend را بر عهده دارد.

در پروژه‌های بزرگ، ممکن است این دو سرویس از یکدیگر جدا باشند، اما برای اکثر پروژه‌های Django استفاده از Redis برای هر دو نقش، انتخابی مناسب و رایج است.

---

## `CELERY_ACCEPT_CONTENT`

```python
CELERY_ACCEPT_CONTENT = ["json"]
```

این تنظیم مشخص می‌کند Worker فقط چه نوع داده‌هایی را دریافت کند.

در این کتاب تنها از JSON استفاده خواهیم کرد.

این انتخاب چند مزیت دارد:

* مستقل از زبان برنامه‌نویسی است.
* خوانایی بالایی دارد.
* از نظر امنیتی نسبت به فرمت‌هایی مانند `pickle` مناسب‌تر است.

به همین دلیل مستندات رسمی Celery نیز در اکثر سناریوها استفاده از JSON را توصیه می‌کنند.

---

## `CELERY_TASK_SERIALIZER`

```python
CELERY_TASK_SERIALIZER = "json"
```

قبل از ارسال هر Task به Redis، Celery باید داده‌های آن را به رشته‌ای قابل انتقال تبدیل کند.

این فرآیند **Serialization** نام دارد.

در این پروژه، تمام Taskها با فرمت JSON سریال‌سازی می‌شوند.

---

## `CELERY_RESULT_SERIALIZER`

```python
CELERY_RESULT_SERIALIZER = "json"
```

همانند ارسال Task، نتیجه اجرای آن نیز باید قبل از ذخیره شدن سریال‌سازی شود.

برای جلوگیری از ناسازگاری، از همان فرمت JSON استفاده می‌کنیم.

---

## `CELERY_TIMEZONE`

```python
CELERY_TIMEZONE = TIME_ZONE
```

به جای نوشتن مقدار ثابت مانند `"UTC"`، از متغیر `TIME_ZONE` پروژه Django استفاده می‌کنیم.

به این ترتیب، تمام اجزای پروژه از یک منطقه زمانی مشترک استفاده خواهند کرد و در آینده هنگام استفاده از Celery Beat یا زمان‌بندی Taskها، اختلاف زمانی ایجاد نخواهد شد.

---

# چرا از متغیر `TIME_ZONE` استفاده می‌کنیم؟

فرض کنید در فایل تنظیمات Django مقدار زیر تعریف شده باشد.

```python
TIME_ZONE = "Asia/Tehran"
```

اگر در Celery مقدار دیگری مانند `"UTC"` تنظیم شود، زمان اجرای Taskهای زمان‌بندی‌شده ممکن است با انتظار شما متفاوت باشد.

همگام نگه داشتن منطقه زمانی Django و Celery یکی از بهترین شیوه‌های توسعه است.

# گام ششم - بررسی اتصال Redis

قبل از اجرای Worker، بهتر است مطمئن شویم Redis در حال اجرا است.

اگر Redis را روی Host نصب کرده‌اید:

```bash
redis-cli ping
```

خروجی مورد انتظار:

```text
PONG
```

اگر Redis را داخل Docker اجرا می‌کنید:

```bash
docker ps
```

نمونه خروجی:

```text
CONTAINER ID   IMAGE         STATUS
...
redis          Up ...
```

در این حالت نیز می‌توانید اتصال را بررسی کنید.

```bash
docker exec -it redis redis-cli ping
```

و انتظار داریم همان پاسخ زیر را دریافت کنیم.

```text
PONG
```

---

# چرا قبل از اجرای Worker اتصال Redis را بررسی می‌کنیم؟

اگر Redis در دسترس نباشد، Worker نمی‌تواند به Broker متصل شود و در زمان اجرا با خطاهایی مشابه زیر مواجه خواهید شد.

```text
Cannot connect to redis://127.0.0.1:6379/0
```

یا

```text
Connection refused
```

بررسی اتصال Redis پیش از اجرای Worker، یکی از ساده‌ترین راه‌ها برای کاهش زمان عیب‌یابی است.

# گام هفتم - اجرای اولین Celery Worker

اکنون تمام تنظیمات اولیه انجام شده است.

- Celery نصب شده است.
- Django، Celery را شناسایی می‌کند.
- Redis در حال اجرا است.
- فایل‌های پیکربندی ایجاد شده‌اند.

اکنون می‌توانیم اولین Worker را اجرا کنیم.

---

دستور زیر را در یک ترمینال جدید اجرا کنید.

```bash
celery -A config worker --loglevel=INFO
```

در این دستور:

- `-A config` مشخص می‌کند برنامه Celery در پروژه `config` قرار دارد.
- `worker` پردازش Worker را اجرا می‌کند.
- `--loglevel=INFO` سطح گزارش‌ها را روی INFO قرار می‌دهد.

این سطح برای محیط توسعه بهترین انتخاب است زیرا هم اطلاعات کافی نمایش می‌دهد و هم خروجی بیش از حد شلوغ نمی‌شود.

---

# اولین اجرای Worker

در اولین اجرا، Celery مراحل زیر را انجام می‌دهد.

1. بارگذاری تنظیمات Django
2. ایجاد برنامه Celery
3. اتصال به Redis
4. جستجوی فایل‌های `tasks.py`
5. ایجاد Queue پیش‌فرض
6. آماده شدن برای دریافت Task

اگر همه چیز به‌درستی پیکربندی شده باشد، خروجی مشابه زیر مشاهده خواهید کرد.

```text
-------------- celery@hostname v5.x
--- ***** -----
-- ******* ----
- *** --- * ---
- ** ---------- [config]
- ** ---------- .> app:         config
- ** ---------- .> transport:   redis://127.0.0.1:6379/0
- ** ---------- .> results:     redis://127.0.0.1:6379/0

[tasks]

[INFO/MainProcess] Connected to redis://127.0.0.1:6379/0

[INFO/MainProcess] mingle: searching for neighbors

[INFO/MainProcess] mingle: all alone

[INFO/MainProcess] celery@hostname ready.
```

ممکن است نسخه Celery یا سیستم عامل شما باعث تفاوت‌های جزئی در خروجی شود.

مهم‌ترین قسمت خروجی، عبارت زیر است.

```text
ready
```

نمایش این عبارت به معنی آن است که Worker آماده دریافت Task است.

---

# چرا بخش `[tasks]` خالی است؟

احتمالاً متوجه شده‌اید که در خروجی Worker قسمت زیر خالی است.

```text
[tasks]
```

این موضوع کاملاً طبیعی است.

در حال حاضر هنوز هیچ فایل `tasks.py` در پروژه ایجاد نکرده‌ایم.

در فصل بعد اولین Task پروژه را خواهیم نوشت و پس از اجرای مجدد Worker، نام آن در این قسمت نمایش داده خواهد شد.

---

# بررسی اتصال به Redis

در خروجی Worker، مقدار Transport باید به Redis اشاره کند.

نمونه صحیح:

```text
transport: redis://127.0.0.1:6379/0
```

اگر مقدار دیگری مشاهده کردید، احتمالاً تنظیمات `CELERY_BROKER_URL` به‌درستی انجام نشده است.

---

# اجرای Worker در محیط توسعه

در طول این کتاب، Worker را در یک ترمینال جداگانه اجرا خواهیم کرد.

ترمینال اول:

```bash
python manage.py runserver
```

ترمینال دوم:

```bash
celery -A config worker --loglevel=INFO
```

معماری محیط توسعه به شکل زیر خواهد بود.

```text
                 ┌────────────────────┐
                 │ Django Development │
                 │      Server        │
                 └─────────┬──────────┘
                           │
                           │
                           ▼
                    Redis Message Broker
                           ▲
                           │
                           │
                 ┌─────────┴──────────┐
                 │    Celery Worker   │
                 └────────────────────┘
```

این همان معماری‌ای است که تا پایان فصل سیزدهم از آن استفاده خواهیم کرد.

---

# آیا Worker باید همیشه در حال اجرا باشد؟

بله.

Worker مانند یک سرویس پس‌زمینه (Background Service) عمل می‌کند.

هر Task جدیدی که توسط Django ایجاد شود، تا زمانی که Worker در حال اجرا نباشد، پردازش نخواهد شد.

به همین دلیل در محیط توسعه معمولاً Worker همزمان با Django اجرا می‌شود.

در محیط Production نیز Worker معمولاً توسط ابزارهایی مانند Systemd، Supervisor یا Docker Compose مدیریت می‌شود که در فصل چهاردهم به آن خواهیم پرداخت.

---

| مؤلفه | وضعیت |
|--------|--------|
| Django اجرا می‌شود | ✔ |
| Redis اجرا می‌شود | ✔ |

اگر تمام موارد فوق برقرار باشند، زیرساخت Celery پروژه با موفقیت آماده شده است.

# نکته مهم

در این فصل عمداً هیچ Taskی ایجاد نکردیم.

یکی از اشتباهات رایج در آموزش Celery این است که هم‌زمان چند مفهوم معرفی می‌شود:

- نصب Celery
- تنظیمات
- ایجاد Task
- ارسال Task
- دریافت نتیجه

این روش باعث می‌شود علت بسیاری از خطاها مشخص نباشد.

در این کتاب ابتدا زیرساخت را کامل می‌کنیم و پس از اطمینان از صحت آن، وارد ایجاد Task خواهیم شد.

به همین دلیل اگر Worker اکنون بدون خطا اجرا می‌شود، این فصل با موفقیت به پایان رسیده است.

# تحلیل معماری

در پایان این فصل، اگرچه هنوز هیچ Taskی ایجاد نشده است، اما مهم‌ترین زیرساخت پروژه آماده شده است.

برای درک بهتر، مسیر اجرای برنامه را یک بار دیگر مرور می‌کنیم.

```text
                     Django

                        │

          ایجاد برنامه Celery

                        │

                        ▼

                 config/celery.py

                        │

                        ▼

                 Redis Broker

                        ▲

                        │

                 Celery Worker
```

در این مرحله:

- Django می‌تواند برنامه Celery را مقداردهی اولیه کند.
- Worker می‌تواند تنظیمات پروژه را بخواند.
- Worker به Redis متصل می‌شود.
- Redis آماده دریافت Taskها است.

تنها حلقه‌ای که هنوز به این زنجیره اضافه نشده، ایجاد اولین Task است که در فصل بعد انجام خواهد شد.

---

# چرخه راه‌اندازی پروژه

هر بار که پروژه را اجرا می‌کنید، ترتیب راه‌اندازی به صورت زیر خواهد بود.

```text
۱- اجرای Redis

        │

        ▼

۲- اجرای Django

        │

        ▼

۳- اجرای Celery Worker

        │

        ▼

۴- ارسال Taskها
```

این ترتیب در تمام فصل‌های بعدی نیز حفظ خواهد شد.

در محیط Production نیز همین چرخه برقرار است؛ تنها ابزار مدیریت سرویس‌ها متفاوت خواهد بود.

---

# بهترین شیوه‌ها (Best Practices)

## ۱. فایل `celery.py` را در کنار `settings.py` قرار دهید.

این ساختار توسط مستندات رسمی Celery پیشنهاد شده است و تقریباً در تمام پروژه‌های حرفه‌ای Django استفاده می‌شود.

---

## ۲. تمام تنظیمات Celery را در `settings.py` نگهداری کنید.

از پراکنده کردن تنظیمات در فایل‌های مختلف خودداری کنید.

وجود یک محل واحد برای تنظیمات، نگهداری پروژه را ساده‌تر می‌کند.

---

## ۳. از `autodiscover_tasks()` استفاده کنید.

ثبت دستی Taskها علاوه بر افزایش حجم کد، احتمال فراموش شدن فایل‌های جدید را نیز افزایش می‌دهد.

در اغلب پروژه‌ها، قابلیت شناسایی خودکار بهترین انتخاب است.

---

## ۴. از JSON برای Serialization استفاده کنید.

استفاده از JSON باعث می‌شود:

- داده‌ها خواناتر باشند.
- وابستگی به Python کاهش یابد.
- ریسک‌های امنیتی مرتبط با Serializerهایی مانند `pickle` کاهش پیدا کند.

---

## ۵. از `localhost` در محیط توسعه استفاده کنید.

در این کتاب تا قبل از فصل استقرار با Docker Compose، تمام مثال‌ها بر اساس اجرای محلی (Host) نوشته شده‌اند.

بنابراین مقدار زیر کاملاً صحیح است.

```python
CELERY_BROKER_URL = "redis://127.0.0.1:6379/0"
```

پس از ورود به فصل استقرار، این مقدار متناسب با معماری Docker تغییر خواهد کرد.

---

## ۶. Worker را در یک ترمینال مستقل اجرا کنید.

Worker نباید بخشی از فرآیند اجرای Django باشد.

این دو برنامه مستقل هستند و هر کدام چرخه حیات (Lifecycle) جداگانه‌ای دارند.

# تمرین

## تمرین اول

دستور زیر را اجرا کنید.

```bash
celery -A config worker --loglevel=INFO
```

سپس بررسی کنید که عبارت `ready` در خروجی نمایش داده می‌شود.

---

## تمرین دوم

در فایل `settings.py`، شماره پایگاه داده Redis را از `0` به `1` تغییر دهید.

```python
CELERY_BROKER_URL = "redis://127.0.0.1:6379/1"
```

Worker را مجدداً اجرا کنید و بررسی کنید که همچنان بدون خطا به Redis متصل می‌شود.

---

## تمرین سوم

فایل `config/celery.py` را به‌طور موقت به نام دیگری تغییر دهید و Worker را اجرا کنید.

پیغام خطا را بررسی کرده و علت آن را تحلیل کنید.

پس از پایان تمرین، نام فایل را به حالت اولیه بازگردانید.
