
# فصل ۱ - مقدمه‌ای بر پردازش ناهمگام (Asynchronous Processing)

> **هدف فصل:** درک مسئله‌ای که Celery برای حل آن طراحی شده است و آشنایی با مفهوم پردازش ناهمگام در معماری‌های مبتنی بر Django.

---

# اهداف یادگیری

پس از مطالعه این فصل، خواهید توانست:

* تفاوت پردازش همگام (Synchronous) و ناهمگام (Asynchronous) را توضیح دهید.
* تشخیص دهید چه زمانی استفاده از Celery منطقی است.
* محدودیت‌های اجرای پردازش‌های سنگین در درخواست‌های HTTP را درک کنید.
* نقش Celery را در معماری یک پروژه Django بشناسید.

---

# پیش‌نیازهای فصل

قبل از شروع این فصل:

* پروژه پایه فصل صفر باید آماده باشد.
* Redis و PostgreSQL باید از طریق Docker قابل اجرا باشند.
* پروژه Django بدون خطا اجرا شود.

---

# سناریوی واقعی

فرض کنید در حال توسعه یک سامانه مدیریت صندوق سرمایه‌گذاری هستید.

کاربر وارد پنل می‌شود و روی دکمه **«به‌روزرسانی اطلاعات بازار»** کلیک می‌کند.

این عملیات باید مراحل زیر را انجام دهد:

1. دریافت اطلاعات از API مالی
2. اعتبارسنجی داده‌ها
3. تبدیل داده‌ها به ساختار داخلی سامانه
4. ذخیره در PostgreSQL
5. ثبت گزارش عملیات

در نگاه اول ممکن است تمام این مراحل را مستقیماً در View بنویسید.

```text
Browser
    │
    ▼
Django View
    │
    ▼
Financial API
    │
    ▼
Data Validation
    │
    ▼
PostgreSQL
    │
    ▼
HTTP Response
```

اگر این عملیات تنها چند میلی‌ثانیه طول بکشد، مشکلی وجود ندارد. اما در پروژه‌های واقعی ممکن است دریافت اطلاعات از API چند ثانیه زمان ببرد یا هزاران رکورد نیاز به پردازش داشته باشند.

در این شرایط، کاربر تا پایان عملیات منتظر پاسخ می‌ماند و تجربه کاربری نامناسبی ایجاد می‌شود.

---

# پردازش همگام (Synchronous Processing)

در پردازش همگام، هر مرحله باید به پایان برسد تا مرحله بعد آغاز شود.

```text
HTTP Request
      │
      ▼
دریافت اطلاعات
      │
      ▼
پردازش داده‌ها
      │
      ▼
ذخیره در پایگاه داده
      │
      ▼
ارسال پاسخ
```

در این مدل، تا زمانی که آخرین مرحله تمام نشود، پاسخ HTTP ارسال نخواهد شد.

این روش برای عملیات کوتاه مناسب است، اما برای پردازش‌های زمان‌بر انتخاب مناسبی نیست.

---

# پردازش ناهمگام (Asynchronous Processing)

در پردازش ناهمگام، درخواست کاربر تنها وظیفه ثبت عملیات را بر عهده دارد و اجرای واقعی آن به یک پردازش‌گر مستقل واگذار می‌شود.

```text
HTTP Request
      │
      ▼
ثبت Task
      │
      ▼
HTTP Response
      │
      ▼
──────────────
      │
      ▼
Celery Worker
      │
      ▼
Financial API
      │
      ▼
Database
```

در این مدل، کاربر تقریباً بلافاصله پاسخ دریافت می‌کند و عملیات سنگین در پس‌زمینه ادامه پیدا می‌کند.

---

# آیا همیشه باید از Celery استفاده کنیم؟

خیر.

استفاده از Celery زمانی منطقی است که عملیات مورد نظر یکی از ویژگی‌های زیر را داشته باشد:

* اجرای آن بیش از چند صد میلی‌ثانیه زمان ببرد.
* وابسته به سرویس‌های خارجی باشد.
* نیاز به زمان‌بندی دوره‌ای داشته باشد.
* پردازش حجم زیادی از داده را انجام دهد.
* مستقل از پاسخ HTTP قابل اجرا باشد.

اگر عملیاتی تنها چند میلی‌ثانیه زمان نیاز دارد، استفاده از Celery تنها باعث افزایش پیچیدگی سیستم خواهد شد.

---

# Celery چه کاری انجام می‌دهد؟

Celery یک سیستم اجرای وظایف (Task Queue) است.

به جای اجرای مستقیم عملیات، Django تنها یک Task ایجاد می‌کند.

اجرای آن Task توسط Worker انجام می‌شود.

در فصل دوم، اجزای این معماری را به‌صورت کامل بررسی خواهیم کرد.

---

# بهترین شیوه‌ها

* از Celery برای هر عملیاتی استفاده نکنید.
* ابتدا مدت زمان اجرای عملیات را اندازه‌گیری کنید.
* Taskها را تا حد امکان کوچک و مستقل طراحی کنید.
* درخواست HTTP را از پردازش‌های طولانی جدا نگه دارید.

---

# آنچه به پروژه اضافه شد

در این فصل هنوز هیچ کدی به پروژه اضافه نشده است.

اما یک تصمیم معماری مهم گرفته شد:

تمام عملیات زمان‌بر پروژه از طریق Celery اجرا خواهند شد و هیچ پردازش سنگینی مستقیماً در Viewهای Django انجام نخواهد شد.

این تصمیم پایه تمام فصل‌های بعدی خواهد بود.

---

# جمع‌بندی

در این فصل با مفهوم پردازش همگام و ناهمگام آشنا شدیم و دیدیم که چرا اجرای مستقیم عملیات سنگین در درخواست‌های HTTP انتخاب مناسبی نیست. همچنین مشخص شد که Celery برای جایگزین کردن منطق برنامه نیست، بلکه برای انتقال پردازش‌های زمان‌بر به یک لایه مستقل طراحی شده است.

در فصل بعد، معماری داخلی Celery، نقش Redis، Worker و نحوه تعامل آن‌ها با Django را بررسی خواهیم کرد.

---

# تمرین

۱. سه نمونه از پروژه‌های فعلی خود را نام ببرید که می‌توانند از Celery استفاده کنند.

۲. بررسی کنید کدام‌یک از Viewهای پروژه شما ممکن است به دلیل اجرای عملیات طولانی، زمان پاسخ بالایی داشته باشند.

۳. توضیح دهید چرا استفاده از Celery برای یک عملیات ۵۰ میلی‌ثانیه‌ای معمولاً انتخاب مناسبی نیست.
