## 2. ساخت مسیرها و فایل‌ها با دستورات ترمینال
تمام مسیرها و فایل‌های پایهٔ این فاز باید با **دستورات رسمی فریم‌ورک‌ها یا ابزارها** ساخته شوند تا ساختار مطابق استاندارد همان ابزار باشد.  
هیچ فایل ساختگی دستی ایجاد نکن مگر در جایی که فریم‌ورک خروجی ندارد.

### مثال ساختار اسکلت با دستورات ترمینال:
```bash
# نمونه (برای Django یا FastAPI)
django-admin startproject core_project .
cd core_project
django-admin startapp accounts

# یا در صورت FastAPI
mkdir -p app/{routers,models,schemas,services,tests}
touch app/main.py app/__init__.py app/routers/__init__.py
````

> نکته بسیار مهم: اگر فریم‌ورک ابزار اسکلت‌ساز دارد (مانند Django، NestJS، Flutter)، از آن استفاده کن.
> هدف، **ساخت اسکلت رسمی مطابق استاندارد فریم‌ورک** است نه ایجاد دستی فایل‌ها.

---

## 3. فایل‌ها و مسیرهای تکمیل‌شده در این فاز

درخت مسیر نهایی پس از اجرای دستورات بالا، همراه با توضیح نقش هر فایل.
از ساختار درختی (Tree) استفاده کن.

### مثال:

```
project-root/
├── app/
│   ├── main.py
│   ├── routers/
│   │   └── user_router.py
│   ├── models/
│   │   └── user_model.py
│   └── services/
│       └── auth_service.py
├── tests/
│   └── test_auth.py
└── requirements.txt
```

### نقش فایل‌ها (با اصول طراحی)

| فایل            | نقش                         | اصل طراحی مرتبط                      |
| --------------- | --------------------------- | ------------------------------------ |
| main.py         | نقطه ورود برنامه            | SRP (Single Responsibility)          |
| user_router.py  | کنترلر سطح API برای کاربران | Clean Architecture (Interface Layer) |
| user_model.py   | تعریف مدل کاربر             | DDD (Entity)                         |
| auth_service.py | منطق احراز هویت             | SOLID (Dependency Inversion, SRP)    |

## 4. اصول طراحی و معماری در این فاز

در این بخش مشخص کن که چگونه این فاز با اصول مهندسی سازگار است:

| اصل                    | توضیح کاربرد در این فاز                                                   |
| ---------------------- | ------------------------------------------------------------------------- |
| **Clean Architecture** | جداسازی لایه‌ها: Presentation / Domain / Infrastructure                   |
| **SOLID**              | پیاده‌سازی SRP و DIP در سرویس‌ها و مدل‌ها                                 |
| **DDD**                | تفکیک Entity، Repository، و UseCase                                       |
| **Design Patterns**    | الگوهای مورد استفاده: Factory برای ساخت اشیا، Repository برای دسترسی داده |
| **Layered**            | تقسیم واضح بین لایهٔ API، Domain، و Data                                  |
| **Versioning**         | نسخه‌بندی API (v1, v2) از ابتدا اعمال شود                                 |

## 5. روش تست فاز

در این بخش روش‌های کلی تست برای اطمینان از صحت فاز توضیح داده می‌شود (بدون کد).

| نوع تست          | ابزار               | هدف                          | توضیح                         |
| ---------------- | ------------------- | ---------------------------- | ----------------------------- |
| Unit Test        | pytest / unittest   | بررسی صحت هر ماژول           | بر اساس SRP                   |
| Integration Test | pytest / requests   | تست ارتباط ماژول‌ها          | API ↔ DB ↔ Service            |
| Contract Test    | Pact / Schemathesis | هماهنگی بین Backend و Mobile | در صورت وجود                  |
| E2E Test         | behave / robot      | اعتبارسنجی جریان کامل        | پس از ادغام فاز با دیگر فازها |

> رعایت اصول TDD/BDD اگر مرتبط است، توصیه می‌شود.
