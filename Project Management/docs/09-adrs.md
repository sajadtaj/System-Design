## 🎯 هدف فایل `adrs.md` (Architecture Decision Records)

### 1. تعریف

**ADR (Architecture Decision Record)** سندی کوتاه، رسمی و قابل‌نسخه‌سازی است که **هر تصمیم مهم معماری** را با دلایل، گزینه‌ها و پیامدهایش ثبت می‌کند.
به‌عبارتی، ADR تاریخچهٔ تفکر معماری پروژه است — چرا تصمیمی گرفته شد، در چه شرایطی، و با چه گزینه‌های جایگزین.

---

### 2. فلسفه وجودی

در پروژه‌های فنی پیچیده، معماری در طول زمان تغییر می‌کند.
اگر تصمیم‌ها مستند نشوند:

* دلایل انتخاب‌ها فراموش می‌شوند،
* اعضای جدید تیم بدون درک زمینه، تصمیم‌های تکراری یا ناسازگار می‌گیرند،
* تحلیل تأثیر تغییر (Impact Analysis) دشوار می‌شود.

ADR این مشکل را حل می‌کند، چون:

* هر تصمیم را به **زمان، زمینه و منطقش** متصل می‌کند.
* مسیر تغییر و تکامل معماری را شفاف و قابل‌ردیابی می‌سازد.
* در Code Review یا طراحی فازهای بعدی، به‌عنوان مرجع عمل می‌کند.

---

### 3. هدف اجرایی در پروژه

در این پروژه، فایل `docs/09-adrs.md` هدفش این است که:

1. **ثبت تصمیم‌های کلیدی معماری** در طول مسیر توسعه (برای کل سیستم یا هر فاز).
2. **مستندسازی دلیل انتخاب‌ها** (چرا این الگو، چرا این ابزار، چرا این ساختار).
3. **تحلیل گزینه‌های جایگزین** (چه انتخاب‌هایی بررسی شد و چرا رد شدند).
4. **ارتباط با سایر اسناد**:

   * از **`04-architecture.md`** منبع می‌گیرد (پایهٔ تصمیم‌ها)
   * به **`06-phasing.md`** و **`07-milestones`** بازتاب دارد (تأثیر اجرایی تصمیم‌ها)
   * در **`08-docs-phase`** به‌عنوان مرجع تصمیم‌های پیاده‌سازی استفاده می‌شود

---

### 4. چه چیزهایی در ADR ثبت می‌شود

* تصمیم دربارهٔ سبک معماری (مثلاً Microservices vs Layered)
* انتخاب فناوری‌ها (PostgreSQL vs MongoDB, FastAPI vs Django)
* سیاست امنیتی (JWT vs Session-based)
* انتخاب روش استقرار (Docker Compose vs Kubernetes)
* تصمیم درباره Observability (Prometheus + Grafana vs ELK)
* سیاست داده و Backup
* قرارداد API (REST vs GraphQL)
* تغییرات اساسی در ساختار دامنه یا Contextها

> نکته: در ADR تصمیم‌های کوچک سطح کد (مثل انتخاب نام تابع یا refactor جزئی) نمی‌آیند — فقط تصمیم‌های **معماری و سیستمی با اثر پایدار**.

---

### 5. زمان ایجاد ADR

* **پیش از شروع هر فاز جدید** (اگر تصمیمی کلیدی وجود دارد)
* **در حین توسعه یک فاز** (اگر تغییر طراحی لازم شد)
* **بعد از تکمیل یک فاز** (اگر تصمیم جدید تثبیت شد یا تصمیم قدیمی کنار گذاشته شد)

---

### 6. ساختار پیشنهادی هر ADR

در فایل `adrs.md` می‌توان هر تصمیم را به‌صورت خلاصه ثبت کرد یا هر تصمیم را در فایل جداگانه در پوشه `docs/09-adrs/` نگه داشت.
هر رکورد باید شامل موارد زیر باشد:

| بخش                        | توضیح                                                |
| -------------------------- | ---------------------------------------------------- |
| **شناسه (ID)**             | شماره تصمیم (مثلاً ADR-001)                          |
| **عنوان تصمیم**            | یک عنوان کوتاه (مثلاً انتخاب پایگاه داده PostgreSQL) |
| **وضعیت**                  | Proposed / Accepted / Deprecated / Superseded        |
| **زمینه (Context)**        | توضیح شرایطی که تصمیم در آن گرفته شد                 |
| **گزینه‌ها (Options)**     | راه‌حل‌های بررسی‌شده و نقاط قوت/ضعف هرکدام           |
| **تصمیم (Decision)**       | گزینهٔ انتخاب‌شده                                    |
| **دلایل (Rationale)**      | چرا این گزینه انتخاب شد                              |
| **پیامدها (Consequences)** | تأثیرات مثبت و منفی تصمیم                            |
| **تاریخ و نویسنده**        | تاریخ ثبت و نام تصمیم‌گیرنده یا تیم                  |
| **ارجاعات**                | لینک به فاز، مایلستون، یا سند مرتبط                  |

---

### 7. ارزش عملی ADR برای تیم تو

برای پروژه‌ای مثل تو که:

* ساختار **ماژولار و چند‌فازی** دارد،
* هر فاز **وابسته به تصمیم‌های قبلی** است،
* و تمرکز ویژه بر **Clean Architecture و DDD** دارد،

ADR کمک می‌کند تا:

1. مسیر تصمیم‌ها شفاف بماند (در code review یا onboarding اعضای جدید).
2. فازها با تصمیم‌های ناسازگار ساخته نشوند.
3. امکان rollback معماری یا مهاجرت فناوری به‌صورت آگاهانه فراهم شود.
4. پیوستگی میان **Phasing → Milestones → Docs-Phase** حفظ شود.
